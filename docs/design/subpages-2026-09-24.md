# Secondary screens — design and implementation (2026-09-24, rev 4)

Reviewed in native Claude Design and implemented in SwiftUI. Rev 4 (2026-09-25)
keeps provider names visible when native menus flatten their section headers.
Security confirmations, approval authorization, share delivery and native composer focus remain intact.

- Canvas (native Claude Design, 21 artboards): <https://claude.ai/artifact/Sw1Xbkwmg8vkUzgqQJ1YbT>
- Standalone previews from the same markup, one HTML per board, light and dark by `data-theme`:
  [`subpages-previews/index.html`](subpages-previews/index.html). Open in any browser; no runtime needed.
- Editable artboards live in the linked canvas; standalone HTML previews are checked in here.

The canvas is private until shared from its Share menu.

## Prototype-only conventions that must NOT carry into SwiftUI
- Fixed artboard heights and `overflow:hidden` exist so the canvas has frames. SwiftUI lists and
  forms keep their natural, scrolling height; nothing gets a fixed height except the QR image.
- Coding-agent tiles use a neutral glyph on the canvas. Production keeps `AgentMarkView` with
  the real provider assets (the marks are not redrawn in a mockup).
- Menus are drawn as static popups. Production keeps the existing native `Menu` + `Picker`,
  `.menuStyle(.button)`, `.buttonStyle(.plain)`, `.menuIndicator(.hidden)`, the accessibility
  identifier `runSettingsMenu`, label "Model and effort", and the accessibility value.
- Copy in the boards is literal so viewers can retype it; the app keeps `String(localized:)`.

## What changes per screen (and what does not)

### iOS Settings (`apps/ios/.../SettingsView.swift`)
- Warm canvas + paper rows: `.scrollContentBackground(.hidden).background(YorozuPalette.canvas)` and
  `.listRowBackground(YorozuPalette.paper)`, same as `NewThreadPicker.paperList()`. Tint `.yorozuTint()`.
- Header "Mac" → "Your Mac". Status: dot + label in one colour: sage connected, warn "Mac offline",
  secondary "Reconnecting" (existing state, not drawn; same row treatment).
- Relay row: label above, value below, monospaced, wrapping, `.textSelection(.enabled)`. Never
  truncated: a relay URL is a value the user may need to read back in full.
- Approvals, three distinct states, never implying a grant before the host gives it:
  1. Off, nothing pending → footer "Uses each agent’s approval settings. Turning this on requests
     permission from your host Mac."
  2. Requested, host not yet granted (`yoloPending`) → switch stays **off**, footer shows the
     spinner line "Waiting for the Mac to allow it" above the same helper. No expiry.
  3. Active (`yoloMode`) → switch on, red-triangle warning "Every tool request runs without
     asking…", then "Until 6:30 PM". No pending line.
- Unpair row gets a footer that says what is lost; alert copy unchanged.
- Version, GitHub link, provider-mark notice as today. Demo mode (Exit demo instead of Unpair,
  Mac and Approvals sections hidden) is unchanged and not drawn.

### Share composer (`ShareComposeView.swift`)
- Structure unchanged: preview → note → Send to. Link icon and quotation rule in vermilion;
  thread symbols in secondary ink, not blue; checkmark vermilion.
- Send enablement follows `canSend` exactly: link/text/picture enabled; picture over 5 MB
  (`MessageAttachment.maxBytes`) **always** disabled with the warn footer "That picture is over
  5 MB. Send it from the app instead."; unsupported disabled until a note is typed, because a note
  on its own is a message. Unsupported footer: "Nothing here Yorozu can carry, but a note on its
  own is a message."
- Send-to footer: **"If Yorozu doesn’t open, open the app to finish sending. Shares wait for your
  Mac to reconnect."** Matches `ShareViewController.hand(over:)`: the file is written first, the
  app drains it on next foreground if `open` is refused.
- Keep: note focus only after the item loads and never during showcase; "New session" default;
  loading row while reading the item.

### New thread (`NewThreadPicker.swift`)
- Already on-token. Kept as is: serif question, 36 pt mark tile, two-step stack, recent/other,
  refresh row disabled while loading/offline, wrapping paths (drawn monospaced 12 pt; optional).
- Offline or failed with cached folders: the existing one-line banner above the list is the whole
  signal. Rows stay fully opaque and selectable (dimming failed contrast: 2.96:1 light, 3.82:1 dark).
- Empty states unchanged (`ContentUnavailableView` for ready-empty/offline/failed, spinner for loading).

### Model and effort (`ChatView.runSettingsButton`, stays native `Menu` + `Picker`)
- Trigger chip: `Model · effort` as today, secondary colour, chevron, 44/28 pt target.
- Top level shows two submenus, "Model" and "Effort", each showing its current value (native
  `Picker` inside `Menu` on iOS 17+/macOS 14+).
- Model list: `Auto` first, on its own; then one `Section(option.providerLabel)` per provider,
  with every row reading `option.menuLabel` ("Claude · claude-sonnet-5"). The OS owns the menu's
  layout: iOS 27 flattens the Sections to separators and drops the header text (simulator
  validation, 2026-09-25), and neither submenus, headers nor exact ordering are guaranteed on
  any release. The row therefore names its provider itself. Effort list unchanged: "Default"
  then `model.efforts(for:)`. Empty catalog shows only Auto/Default, as now.
- Provider/runtime semantics untouched: `models(for: thread)` per agent, effort list per model.
- macOS: the two disabled "Current model / Effort" lines stay at the top of the NSMenu.
- No custom overlay, no sheet, no keyboard change: the performance and focus fixes from
  `docs/history/native-ui-performance-2026-09-20.md` are untouched.

### macOS Settings (`GeneralSettings.swift`, `DevicesView.swift`, `PermissionsView.swift`, `RelaySettings.swift`)
- Same paper/canvas treatment on the grouped Form so the three tabs read as one family with the
  phone; vermilion accent already lands via `Accent.xcassets`.
- Tabs: host shows General / Devices / Permissions; a **client shows General only** (as
  `ChatWindowView.SettingsView` already does).
- General host: This Mac (segmented role + relay field) · Agent runtime (YOLO) · Stay available ·
  Updates · marks notice. Content is ~760 pt in the fixed 600×620 window and **scrolls; keep the
  scroll and every lifecycle control** (Start at login, Keep Yorozu running, Never sleep,
  automatic updates, beta updates, Check for Updates).
- General client: Connection row with dot + `ClientConnectionStatus.label`, hint text, Retry,
  "Retrying keeps your pairing and conversations.", Paired since, Unpair…; all existing. States
  not drawn but unchanged: unpaired (pairing-code field + Connect), connecting (spinner), failed
  (red failure text + hint), offline.
- Devices: rows unchanged in content; device-ID disclosure and Remove… per remote device; online
  dot sage; Relay status below. Confirmation dialogs unchanged.
- Pairing sheet: QR / paired / unavailable drawn. Baseline loading ("Checking paired devices…"),
  baseline failure ("Couldn’t load paired devices" + Try again) and "Preparing a pairing code…"
  are unchanged and not drawn; the code is never shown before the device baseline is known.
- Permissions: all four sections kept: Stay available · Control this Mac · Files · **Apps and
  personal data** (Calendars, Reminders, Contacts, Photos, Music, Location, Camera, Microphone).
  Row = title / badge / detail / small buttons right-aligned. Badges: sage Granted, secondary
  Waiting…, hourglass Asking macOS…, switches for Start at Login and Never Sleep. Setup wizard row last.

## Acceptance (widths, keyboard, accessibility)
- Compact iPhone (390): every board as drawn. iPad and Mac widths: the same lists inside the
  sheet (`NewThreadPicker` min 380×440 on Mac; `insetGrouped` on iPad keeps the 16 pt gutter, rows
  do not stretch content past `LayoutMetrics.readingWidth`).
- Model menu with the keyboard up (iOS): the native `Menu` opens above the composer without
  resigning first responder; the draft and caret stay; when the composer was not focused, opening
  and closing the menu does not summon the keyboard. This is existing behaviour and is the
  acceptance test for any chip/label change.
- Dynamic Type: footers, paths, relay value and permission details wrap; nothing is fixed-height
  except the QR.
- Tappable rows are `<button>`, links `<a>`, fields `<input>` with labels; selected destination
  rows are `role=radio`. SwiftUI keeps `accessibilityAddTraits(.isSelected)`, `accessibilityHint`
  on agent rows, `accessibilityValue` on the model chip, `accessibilityLabel` on status dots.
- Status never by colour alone: dot + word; granted = icon + word.

## Verification

On the isolated design branch based on current `main`:

- Shared Swift package: **274 tests passed**.
- Mac app: **build and 9 tests passed**.
- Both bundle scripts: shell syntax checked; each accent compilation produced `Assets.car`.
- Native iPhone settings and share screens inspected. Provider-qualified model rows inspected
  with the software keyboard visible; rows wrap without dropping the provider name.
- Final iOS simulator build and keyboard regressions: **4 passed** (2 each on iPhone and iPad, iOS 27).
  Model/effort selection keeps the keyboard and draft; opening an unfocused picker does not summon it.
- Native Claude Design canvas and representative light/dark HTML previews visually reviewed.

Native menu separators, headers, submenus and ordering depend on the OS. Acceptance is complete
provider/model names and selectable Auto, not a fixed arrangement. Physical-device IME behavior,
maximum accessibility text size and native Mac dark-form appearance still need device review.
