## Finding

Signal does expose agent progress. Its implementation combines lifecycle reactions on the triggering user message, refreshed typing indicators, and optional completed reply blocks. It does **not** implement the editable progress-draft transport used by Telegram/Discord. Signal's schema uses delivery-streaming configuration, and its channel handler installs lifecycle callbacks rather than a draft editor. [Signal schema](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/config-schema.ts#L117), [Signal handler](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/monitor/event-handler.ts#L573).

Official documentation lists Signal typing and status reactions separately. The progress-draft transport table includes Discord, Matrix, Teams, Slack, Telegram, and Mattermost; channels without safe editing use typing/final delivery. [Signal docs](https://docs.openclaw.ai/channels/signal#typing--read-receipts), [Progress-draft transport table](https://docs.openclaw.ai/concepts/progress-drafts#channel-behavior).

## Signal lifecycle

The handler requires status reactions enabled, reaction level other than `off`, an ack reaction allowed by scope, and a usable inbound timestamp. Group targets additionally identify the original author. Queue admission calls `setQueued`; recording calls `setThinking`. Reply options explicitly preserve progress/tool callbacks when source delivery or ordinary progress is hidden. `onToolStart` calls `setTool(name)`; compaction start/end calls `setCompacting`, then cancels pending state and returns to thinking. Final status depends on visible reply delivery, delivery failures, and agent terminal failure. [Handler gates](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/monitor/event-handler.ts#L336), [Callbacks/finalization](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/monitor/event-handler.ts#L563).

The shared controller maps thinking to 🧠, generic tools to 🛠️, coding/web categories to 💻/🌐, compaction to 🗜️, success/error to ✅/❌. Queue uses the configured initial ack. Updates serialize, debounce for 700 ms, and skip repeated sends. No activity for 10/30 seconds produces stall indicators; Signal maps both stalls to ⏳ because its single reaction slot could make a warning look terminal. Completion seals the controller, clears timers, holds success/error for 1.5/2.5 seconds, then Signal restores the original ack. Adapter failures are caught and reported through logging. [Shared controller](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/src/channels/status-reactions.ts#L57), [Signal stall override](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/monitor/event-handler.ts#L388), [Signal final restoration](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/monitor/event-handler.ts#L162).

Typing starts through the channel reply pipeline and `sendTyping`; username targets return unsupported. Signal's handler supplies a start callback, not an explicit stop callback. Do not claim every terminal state sends `sendTyping(stop: true)`. The shared typing controller stops its keepalive loop after run completion and dispatch idle, seals against late callbacks, and has TTL/fallback cleanup. [Signal typing wiring](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/monitor/event-handler.ts#L406), [Signal RPC](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/send.ts#L364), [Typing controller](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/src/auto-reply/reply/typing.ts#L93).

## Streaming, formatting, placement

Completed blocks become ordinary channel messages; preview streaming is a separate mechanism. Signal defaults block coalescing to 1500 characters / 1000 ms idle. Its outbound text is converted from Markdown into plain text plus native style ranges (bold, italic, strike, monospace, spoiler), then sent through `send`. This transport does not demonstrate incremental Markdown parsing in a native Yorozu message view. [Streaming distinction](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/docs/concepts/streaming.md#L10), [Signal defaults](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/shared.ts#L101), [Formatting](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/format.ts#L28), [Formatted send](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/extensions/signal/src/send.ts#L274).

Signal progress reactions remain attached to the inbound user message. That placement does not meet this user's request for progress below the latest message. The relevant upstream placement precedent is **Telegram**: its documented progress draft reposts below intervening messages rather than jumping the user's scroll position. Yorozu can position a native progress row below the latest message without reproducing remote send/delete transport. [Telegram placement](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/docs/concepts/progress-drafts.md#L432).

## Yorozu comparison

Current local integration already has finer tool detail than Signal reactions:

- [`progress.js`](../../packages/openclaw-channel/progress.js): observe-only `before_tool_call` / `after_tool_call`, scoped to `requester.channel === "yorozu"`, matched by `toolCallId` to the active session run. Sends `tool_started` with name/args and `tool_finished` with success/output; exceptions cannot affect tool execution.
- [`runs.js`](../../packages/openclaw-channel/runs.js): runs serialize per thread; `run_started` / `run_finished` distinguish completed, failed, aborted. Boundaries journal and replay after reconnect.
- [`dispatch.js`](../../packages/openclaw-channel/dispatch.js): delivery pipeline, abort signal, and terminal outcome callback. No Signal-style compaction callback or typed in-tool progress callback wired here.
- [`channel.js`](../../packages/openclaw-channel/channel.js): text deliveries become ordinary Yorozu messages; no answer-preview update frame.
- [`runtime/channel.ts`](../../packages/runtime/src/channel.ts#L319): tool frames require negotiated run/progress capabilities and validated IDs/types. Tool events are best effort and unacknowledged; boundary replay is not tool-log replay. Existing protocol documented in [`architecture.md`](../architecture.md#channel-progress-progress-v1).

The tool-hook map removes entries on `after_tool_call`; it has no explicit run-terminal cleanup. If OpenClaw omits an after hook during exceptional cancellation, a pending entry could remain. This is a code-path risk, not a reproduced leak.

## Recommendations (inference; no implementation in this study)

1. Keep existing run/tool protocol. Render one native activity region below the latest message across iPhone, iPad, and Mac. Reuse stable run and tool IDs; never move progress by rewriting message timestamps.
2. Learn Signal's lifecycle discipline: distinguish waiting, running, tool activity, compaction, success, failure, and cancellation; ignore late events after a terminal boundary. A tool failure is not automatically a failed turn. Yorozu supports successful no-reply runs, so do not copy Signal's visible-reply success condition.
3. Keep active progress transient; retain tool diagnostics in the existing trace. Clear spinners on terminal boundaries and known disconnection; let boundary replay restore an actual active run. Do not invent completion from a lost tool-finish event.
4. If richer OpenClaw progress is requested, use official per-turn reply callbacks (Signal proves `onToolStart`, `onCompactionStart/End` exist) and explicitly public typed progress. Negotiate any new frame/capability and validate at the host. Generic public labels avoid displaying raw args/output as status. Existing private diagnostic trace can remain distinct.
5. Treat streaming Markdown as its own native rendering concern. Current OpenClaw deliveries are completed texts/blocks; frontend support cannot manufacture token deltas. A future incremental transport needs message identity/update semantics and terminal reconciliation before the native view can stream that source.

No feature code changed. No upstream tests executed; conclusions come from pinned official source and current local integration reads.

## Follow-up: actual Yorozu streaming gap and ordering review

Follow-up requested while the UI fixes were being prepared. Installed `/opt/homebrew/lib/node_modules/openclaw/package.json` also declares `2026.9.6`, but its schema versions differ from the inspected upstream `main`; installed artifact and pinned source are distinct evidence.

### Partial text is available through the public SDK

The installed SDK's channel turn options accept `onPartialReply` and `onAssistantMessageStart`. The former receives sanitized partial text, optionally `delta` and `replace`; the latter marks a new assistant message, including after a tool/thinking phase. `ChannelTurnReplyOptions` omits the block-delivery callbacks, not these partial callbacks. Installed declaration locations: `dist/templating-0ElMwhje.d.ts:1770,1882` and `dist/plugin-entry-CACNQ1z6.d.ts:43951`. Matching public definitions: [PartialReplyPayload](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/src/auto-reply/get-reply-options.types.ts#L117), [GetReplyOptions callbacks](https://github.com/openclaw/openclaw/blob/c1fb7e853f8301ef5a9f01ceeac6d63e19124c15/src/auto-reply/get-reply-options.types.ts#L240).

Installed runtime `dist/dispatch-from-config-Cu599NRF.mjs:1347` forwards the partial callback and records accepted visible partials. `dist/agent-runner.runtime-DH-TOu7I.mjs:2490` wraps embedded-agent partials into sanitized text snapshots with a memoized getter. Consume `payload.text` as authoritative at this layer; do not require raw token deltas. Return `false` until channel-visible progress has actually been accepted. `preserveProgressCallbackStartOrder` is available for stateful channel renderers. Ordinary global tool/message-delivery/model-output hooks do not supply this growing-answer stream.

Yorozu currently wires neither partial callback in [`dispatch.js`](../../packages/openclaw-channel/dispatch.js). [`socket.js`](../../packages/openclaw-channel/socket.js#L123) creates a new UUID for each delivery; [`runtime/channel.ts`](../../packages/runtime/src/channel.ts) recognizes immutable acknowledged deliveries; [`serve.ts`](../../packages/runtime/src/serve.ts#L3176) ignores an already logged delivery ID and records every accepted channel reply with `done: true`. Consequently OpenClaw response text never reaches the native streaming path, even though completed Markdown renders correctly.

The native side already supports growing messages: [`ChatModel.upsert`](../../packages/shared-swift/Sources/YorozuShared/ChatModel.swift#L3115) replaces events sharing an ID and rejects stale partials after a final; [`streamingMessageId`](../../packages/shared-swift/Sources/YorozuShared/ChatView.swift#L2342) selects unfinished agent messages; [`MessageBubble`](../../packages/shared-swift/Sources/YorozuShared/MessageBubble.swift#L397) calls `MarkdownText(cursor: streaming)`. [`MarkdownText`](../../packages/shared-swift/Sources/YorozuShared/MarkdownView.swift#L16) parses Markdown during those updates on all platforms. This is a transport gap against the user's request when the agent is OpenClaw, not an absence of streaming Markdown support in the view.

Minimal transport recommendation: negotiate an answer-update capability; use stable run/message identity plus update ordering; publish unfinished sanitized snapshots through the existing message event; reconcile an acknowledged durable final into that same message. Rotate message identity on `onAssistantMessageStart`, gate updates to the active run, ignore late updates after terminal settlement, and seal partial text on failure/cancellation. Keep ordinary block delivery from duplicating the same answer. Never emulate streaming by slicing a completed answer. Preserve a message's placement timestamp while its text grows; the Swift model reorders events when timestamps change.

### Review of progress placement in the production path

The current [`AgentTrace.chatRows`](../../packages/shared-swift/Sources/YorozuShared/AgentTrace.swift#L466) moves running work after the latest reply within its turn. User/unreadable boundaries stop the move. Host `activeEventId` keeps work live after a channel reply with `done: true`; only the host's terminal run state settles it. On settlement, work returns above completed replies. This produces a visible completion-time layout change; it is intentional in the implementation, not evidence that the host ended a run prematurely.

A standalone `chatRows` input containing `U1 active → U2 queued → tool(U1)` would misattribute later work to U2. **That is not a valid normal production repro:** [`ChatModel.rows`](../../packages/shared-swift/Sources/YorozuShared/ChatModel.swift#L187) removes queued/withdrawn IDs before grouping, then appends queue bubbles afterward. Do not broaden turn grouping on the basis of that isolated helper input.

The actual queued-message output is `U1 → reply → live work → U2 queued`. Therefore live work is above the latest queued bubble. Furthermore [`chatActivity`](../../packages/shared-swift/Sources/YorozuShared/ChatActivity.swift#L62) suppresses generic thinking only when the final row is live work. A queued final row can create an additional thinking indicator below the queue when no unfinished reply exists. Minimal correction depends on intended queue placement: move running work after appended queue bubbles if “below latest message” includes queued requests, or suppress fallback thinking whenever a live work row is already visible. Neither requires changing event ownership or host run boundaries.

Finally, `chatRows` moves all `done: true` agent messages after other events within a user turn. Channel block replies each have `done: true` although the run can continue. This normalizes chronology and may combine activity preceding multiple channel replies. Keep tests/scenarios for multi-reply runs and terminal layout; do not treat `done` on a channel message as `run_finished`.
