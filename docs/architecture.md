# Architecture

How Yorozu v2 is put together and how a message moves through it. Harness call details are in [openclaw-integration.md](openclaw-integration.md) and [hermes-integration.md](hermes-integration.md), the phone wire format in [ios-relay-contract.md](ios-relay-contract.md), and file paths in [setup.md](setup.md#where-data-lives).

```
 Mac popover ───┐                         ┌── main harness, one of:
                ├─> Engine ─> Store       │   OpenClawHarness ── WebSocket or CLI ── local Gateway (agent [harness] agent)
 iPhone ─ relay ┘     │      (SQLite)     │      roles (raw model runs), topic sessions, Claude Code / Codex in worktrees
   (RelayHost +       ├─> MemoryStore ────┤   HermesHarness ── HTTP + SSE ── local Hermes API server (profiles yorozu-*)
    EngineBridge)     │   (Markdown+FTS5) │      roles (one-shot runs), topic sessions, Hermes coding in its own worktree
                      └─> Harness ────────┘   FixtureHarness / OfflineHarness for the other modes
```

### Run modes

`PROJECTX_MODE` picks the mode, and in live mode `[harness] kind` picks the harness ([setup.md](setup.md#environment-variables)).

| Mode | Harness | Behaviour |
|---|---|---|
| `live` (default) | `OpenClawHarness` (`kind = "openclaw"`, the default) or `HermesHarness` (`kind = "hermes"`) | Real models through the main harness: the local Gateway on the configured agent (`[harness] agent`), or the local Hermes API server. Starts the relay. |
| `fixture` | `FixtureHarness` | Scripted replies. Orange banner; input stays disabled until "I understand: enable synthetic TEST input" is pressed. Own data root ([setup.md](setup.md#where-data-lives)), no relay. |
| `offline` (also any invalid value) | `OfflineHarness` | Messages are saved; routing posts the failure "Offline mode: message saved; no model was called…". |

The first message sent binds the data directory to its run mode, `live` or `fixture` (receipt id `runtime-binding`); sending from another mode is then refused. Offline mode never binds. The binding is to the mode, not the harness, so live harnesses can be switched over the same data; bodies written before #318 hold the harness's display name ("Configured OpenClaw · live acceptance unverified", "Synthetic fixture · NOT a live model") and read as their mode, so no migration is needed.

## Harness seam

`Harness` (`Harness.swift`) is what the Engine calls: `route`, `run`, `steer`, `cancel`, `reconcile`, `extract` and `models`, plus these members:

- `id`: the stable harness id, `openclaw`, `hermes`, `fixture` or `offline`. The Engine binds data by mode from it; request receipts and the `harness-kind` receipt record it.
- `executors`: the coding executors the harness offers, in preference order; an empty list (fixture, offline) means no coding work. Each `Executor` has an `id` (stored in `work.executor`), a display `name`, `appAccess` (gets Yorozu's MCP servers, so it can operate apps and browsers), `liveSteer` (takes changes mid-run), `routingNotes` (harness-specific guidance for the secretary), `notReady` (nil when ready, else why) and `runtime` (the model runtime its automatic model is picked for, matched against `ModelInfo.runtimes`). OpenClaw offers `claude` (Claude Code, runtime `claude-cli`) and `codex` (Codex, runtime `codex`), neither steered live; its routing notes carry the rule that new coding work needing an app goes to Codex, since Claude Code gets no MCP servers under OpenClaw. Hermes offers `hermes` ("Hermes", runtime `hermes`), with app access and live steer, not ready while `dev_repo` is empty.
- `rawPromptCap` and `workerGuard`: per-harness limits, by default the shared `rawPromptCap` (20000 bytes, `Models.swift`) and 32000 bytes. The Engine's routing trim measures against the harness's `rawPromptCap`; each adapter checks a worker step against its `workerGuard` before the run handle is stamped. Hermes has no counterpart limits of its own, so its values are Yorozu-side: the shared cap less its role framing, and the default guard.

What the executor list drives in the Engine:

- The routing policy's coding sentence lists only ready executors, each with its name, "cannot operate apps or browsers" when it lacks app access, and its routing notes. The first is the default; a tool the user names wins. A named tool that is not offered gets an offered executor and an instruction that starts with saying in one sentence that the tool isn't available here. With no ready executor the policy says coding work isn't available and never to set `executor`.
- `Engine.validate` accepts an `executor` only when the harness lists it. `delegate` and a retry of stopped work refuse an executor that is not offered or not ready with notice `harness_not_ready`, before anything is created, so a task from another harness's executor stays retryable.
- The steer acknowledgment for work whose executor does not take changes live uses its display name ("<name> can't take changes mid-run…"). An executor the harness no longer offers (after a switch) shows by its id and counts as not live.
- `Store.insertWork` allows one active or uncertain work item per (topic, executor id), thinking work being the null id.
- The automatic coding model per executor is picked for its `runtime` ([setup.md](setup.md#models)).

Prompts: the routing prompt, the thinking contract, the `memoryCall` loop (at most 6 operations), the coding contract, the extraction prompt, `outputRules` and the integration rules (`Prompts.integrationRules`) live in `Prompts.swift`, and both adapters send them unchanged; an adapter adds only transport details (Hermes adds a short role framing and a note that its own memory, skills and scheduled jobs are not the worker's to use). The coding contract takes the base branch and the build command from `HarnessSettings` (`codingBaseBranch` from `[harness] dev_base`, empty meaning the branch checked out in `dev_repo` when the work starts, resolved by `HarnessSettings.resolvingBase`; `buildCommand`, default `scripts/build_native.sh --restart`, no `config.toml` key yet) and, for a harness without managed worktrees, the worktree path and branch the worker creates itself. The worker wire (`WorkerInput.wire`) carries no harness session or controller keys: the topic is only `{id, label}`. `topics.sessionKey`, `work.controllerKey` and `sessionReady` remain as columns each adapter uses its own way.

Request receipts: each adapter writes a `RequestReceipt` (receipt kind `request`) durably before it sends a model run and fails closed when that write fails. It holds correlation data only: request id, `harness` (`openclaw`, `hermes`), session, source message id, the raw-run flag and a state; never prompts, output or credentials. Rows from before #318 have kind `gateway-request` and no `harness`, and are all OpenClaw.

Typed errors: `HarnessError` (`Models.swift`) carries its own notice code: `busy` → `harness_busy` (the harness refused for load, nothing ran), `interrupted` → `run_interrupted`, `approvalRequested` → `approval_requested`, `modelMismatch` → `model_mismatch` (the harness served another model; output discarded), `notReady` → `harness_not_ready`. Each reports how a run ended, so the work fails rather than going uncertain. A context overflow stays `ProjectError.overflow` (`task_overflow`) and a failed compaction a `compaction_failed` notice. A routing error posts the error's code, else `routing_failed`.

Harness choice: `AppModel.liveHarness` (`ProjectX.swift`) builds the adapter named by `[harness] kind` (`PROJECTX_HARNESS` overrides it) after that adapter's launch guard: OpenClaw keeps its exec-shell refusal, refuses agent id `main` (OpenClaw's default agent: workers never run on the user's personal agent; an entry marked `default` is caught by readiness and setup) and otherwise runs on whatever agent `[harness] agent` names; Hermes launches even when not ready, so messages are saved and the status line says what to fix. The `harness-kind` receipt records the live harness each launch ran on. A switch (open question 9 default) applies at the next launch and only when no work is active or uncertain: otherwise that launch stays on the previous harness and the status line says it waits for the running work. Topic workers start fresh sessions on the new harness, and switching back resumes the earlier harness's topic sessions, since each adapter names them from the topic id. Offline and fixture runs take `[harness] agent` as their agent id too, so topic keys keep one prefix in every mode. The popover's status line shows the harness ("OpenClaw Gateway · <agent>", "Hermes Agent") while Ready; readiness ([Setup and readiness](#setup-and-readiness)) covers the rest, a held switch included.

## Flow 1: a Mac message to a result

1. ⌘Return calls `AppModel.send`, then `Engine.send(body, attachments:)`. The body must be 1–6000 UTF-8 bytes, or at most 6000 and possibly empty when files are attached (at most 10, each at most 50 MB; the app downscales images first, [Mac UI](#mac-ui)), and fewer than 32 items may be outstanding (routing + queued + running, job runs not counted). The files are copied into the file store first, then the user `Message` (kind `conversation`) and its `attachments` rows are stored in one transaction, and a failure removes the copies ([Attachments](#attachments)); `send` returns at once; routing runs serially, one message at a time. The bubble's mark reads Delivered from here and Read once `readAt` is set ([Mac UI](#mac-ui)).
2. `Engine.route` first stamps the message's `readAt` (`Store.startRouting`, `UPDATE … WHERE id=? AND readAt IS NULL`); a message already stamped is not routed again ([Restart and resume](#restart-and-resume)). It then builds the `RoutingInput`, a slim view rather than database records (long text is cut by UTF-8 bytes to its head and tail around a `[… cut]` marker):
   - `messageAge`: only for a delayed phone message (stored more than 60 s after its `sentAt`, `Message.delay`), how long ago it was sent ("7 h 16 min"; #314), and the policy gains one sentence saying what it means. Never the device, `sentAt` or `readAt`.
   - `latestTopic`: the topic of the last user message that has one.
   - `topics`: every topic as `{id, label}`, the latest first, then by last activity (its newest message or work item).
   - `files`: only when the message has attachments, one descriptor per file, `{name, type, size, path}` (name ≤ 200 bytes, size as Finder writes it, the absolute path in the file store); never contents (#316).
   - `recent`: the last 4 `conversation`/`result` messages across topics plus the last 3 of `latestTopic`, deduplicated and in time order, as `{role, topicID, taskID, kind, body}`, plus `files` descriptors on a message that has attachments (a user message or a result). A result stored before #311 loses its `Regarding “…”:` header; results are cut to 1500 bytes; other bodies to 1000 bytes. Acknowledgments and failures are left out.
   - With `files` on the message or a recent one, the policy adds that the secretary never sees file contents, that work needing them is delegated (the worker gets the message's files with the task, so the instruction never copies their paths), and that for a message with files and little or no text it acts when recent messages make the intent clear, else clarifies with one short question.
   - `work`: the last 12 work items plus every unsuppressed active or uncertain one, as `{id, topicID, state, executor, instruction, error}` with instruction ≤ 900 bytes and error ≤ 300 bytes.
   - `memory`: hits as `{id, title, excerpt}` (title ≤ 200 bytes, excerpt ≤ 400 bytes), up to 2200 bytes in all.
   - One trim, measured on the final prompt (the longer stronger-review variant, JSON without escaped slashes) against the harness's raw-run cap (`Harness.rawPromptCap`, 20000 bytes on OpenClaw): drop memory hits from the lowest-ranked (kept when the message is a forget request), then finished work oldest first, then the least recently active topics down to 10, then the oldest recent messages, then the remaining least active topics, then the oldest active or uncertain work. The latest topic and the topics of kept work and recent messages are never dropped. Dropped topics and blocking work are counted in an `omitted` field ("N older interrupted tasks and M less active topics omitted"). The policy is printed once, above the data.
3. The secretary (a raw model run on the secretary model) returns a `Decision`: `action` (`reply`, `delegate`, `steer`, `clarify`, `correct`, `retry`, `forget`, `stop`) plus `topicID`, `newTopic`, `taskID`, `instruction`, `reply`, `memoryID`, `executor`. The policy tells it the limits: instruction at most 600 characters, reply at most 1,500, and never copying the user's message into the instruction (workers get it verbatim).
4. The Engine validates it: known action, `executor` is absent or one the harness offers ([Harness seam](#harness-seam)), `topicID` and `taskID` known in the full snapshot (not only the trimmed view), `memoryID` among all retrieved hits, `instruction` ≤ 6000 bytes, `reply` ≤ 15000 bytes, `newTopic` ≤ 80 characters, plus the per-action required fields. It is saved as a `routing` receipt. A `clarify` gets one review on the review model (`routing_escalation` receipt); if that review fails, the clarification stands.
5. For `delegate`, the topic is `topicID`; without one, `latestTopic` when there is no `newTopic`. A `newTopic` reuses an existing topic with the same label (case-insensitive) or creates one with session key `agent:<agent>:projectx:<topicID>` (`projectx` is the app namespace, so agent `projectx` keeps `agent:projectx:projectx:<topicID>`; used by OpenClaw only; Hermes names its sessions `yorozu-<topicID>`). `Store.insertWork` allows one active or uncertain work item per (topic, executor); an uncertain one is reconciled first ([Uncertain blockers](#uncertain-blockers)). No acknowledgment is posted.
6. Lanes: at most 2 thinking runs and 1 coding run at a time, across all topics.
7. `execute` moves the work from `queued` to `working` and builds the `WorkerInput`: topic, work, the request message, earlier same-topic `conversation` messages the session has not seen, memory hits up to 3000 bytes, and the files the work carries (`WorkerInput.attachments`; `Store.insertWork` linked the request message's files when it created the work). The harness runs it (see [Workers](#workers), [Thinking input](#thinking-input) and [Attachments](#attachments)).
8. Files the worker returned (`WorkerOutput.files`) are copied into the file store; then `Store.finish` either turns open amendments into a follow-up turn of the same task (see [Steer](#steer-stop-retry-correct-forget)) or completes it: the result is posted to the main timeline as kind `result`, with topic and `replyTo` set, as the answer alone, with the returned files attached in the same transaction; the UI draws the reply header from `replyTo`, and results stored before #311 keep their `Regarding “…”:` prefix. Memory extraction is queued for it, with a 300-byte excerpt of the `replyTo` message (unless it is a `job_run` trigger) as context the model may not quote.
9. On an error the work becomes `failed` (never dispatched, or a context overflow the Gateway reported) or `uncertain` (it had a run ID), with the error stored up to 1000 bytes, and the timeline gets "That task failed: <error> Say retry to try again." A context overflow (`ProjectError.overflow`) posts its own message instead, with no retry offer ([Context overflow](#context-overflow-and-compaction)).

## Flow 2: a phone message to the same timeline

1. Pairing: Pair iPhone… in Settings › Devices opens the pairing sheet, which has `RelayHost` ask the relay to mint a code. The Mac makes a one-time secret (held only in memory and in the QR) and shows the pairing link as a QR and a link. The phone stores the pairing in its Keychain and dials the relay.
2. Handshake: `RelayHost` accepts a valid `hello` proof or a known device (at most 16), saves `relay-devices.json`, mints a fresh code if the sheet is still open, and runs the peer-info exchange, in which the phone sends its model name ("iPhone 17 Pro") as the device's `name`. A phone counts as online once one of its sealed frames opens on the current relay connection or its direct link, until that socket drops, and each opened frame sets its `lastSeen` ([ios-relay-contract.md](ios-relay-contract.md)).
   - Direct path (#315): with the phone's Direct connection setting on, `RelayClient` races each dial: the Mac's advertised direct candidates at once, the relay about 300 ms later. Each leg runs only phase 1 (socket, join, authenticated `joined`); the first to finish carries the session and runs `hello` and the peer-info exchange alone, and a direct winner cancels the others. A relay winner leaves direct legs running: the first to authenticate takes over make-before-break (`hello` on the direct socket, then the relay socket closes). On the Mac, the listener takes connections only on a private address it would advertise, on a Wi-Fi/Ethernet or `utun` (`.other`) interface. The phone speaks first with a `probe` (room and nonce only); the Mac answers a probe for its own room with `joined` (its key, its proof over the phone's nonce, its own nonce), and only after verifying that does the phone send its `join`. The Mac checks the join against `relay-devices.json` (unknown keys are refused, so pairing stays on the relay), checks every frame's signature against the joined key and opens boxes with that phone's key only. A `hello` on a direct link sets the phone's route to that link and closes any older one (4002); a hello the relay replays from its buffer, or a live relay hello within 2 s of the direct link's own while that link is still heard, leaves a live direct route alone. Both paths carry the same signed frames and the same per-device channel counter; direct frames are never acked to the relay. The Mac drops a joined link silent for more than 30 s and closes every link (4000) on `NSWorkspace.willSleepNotification`, and every new connection (4000) until `didWakeNotification`; a dropped link moves its phone back to the relay route. Every path switch is a new session on the phone: `.paired`, then `sync_request` and the outbox resend. Wire: [ios-relay-contract.md](ios-relay-contract.md#direct-path).
3. Send: the phone puts the message in its outbox and sends it as soon as the relay or the direct path is reachable, even while the Mac is away ([Marks and the outbox](#marks-and-the-outbox)). `RelayHost` opens the phone's sealed `message` event and `EngineBridge.admit` checks it: an event past its `admissionDeadline` (the phone's `ts` + 24 h) gets `admission_status expired` and is never stored, else it calls `Engine.send(text, id:, sentAt:)` with the event's `ts` as `sentAt`. The phone's id becomes the stored message id, so the message joins the same main timeline as the Mac composer and follows Flow 1. Only the text, the id and the send time reach the Engine: no model learns which device a message came from, and neither `RoutingInput` nor the worker wire has an origin field (owner decision). A keyed lookup (`Store.message(id:)`) answers an id already stored with its receipt and no send, and after a failed send tells a duplicate from a refusal. Phone events reach `EngineBridge` one at a time in arrival order.
   - A message with files (#316) never goes through the relay buffer: it waits in the phone's outbox, text included, until the phone has a live session with the Mac (relay or direct) and the Mac advertises `attachments-v1`. The phone then uploads each file in `attachment_chunk`s, one in flight at a time; `EngineBridge` stages them under `~/Library/Application Support/<bundle id>/uploads/<device key>/<message id>/` (`UploadStaging`, fsynced, checked against offset and SHA-256) and answers each with `attachment_progress` and the next offset, so either side resumes after a disconnect or a relaunch. The phone's `attachment_commit` (event id = message id, the text and the descriptors) gets the `message` checks plus the file checks; once every file is staged whole the bridge calls `Engine.send(text, attachments:, id:, sentAt:)`, removes the staging and answers `receipt`, idempotently by message id. Wire: [ios-relay-contract.md](ios-relay-contract.md#attachments).
4. Live updates: on every 350 ms poll, `EngineBridge.publish` reads `Store.changes(after:)` past the last published change sequence and sends the window's changed rows as `message`/`topic`/`task`/`amendment`/`worker_event`/`read_state` records, plus the working and routing flags, to every compatible phone; a moved flag alone sends a live update with no records. The first poll only sets the starting sequence, and a poll whose store read fails sends nothing and leaves the flags for the next one. Records travel under the phone's thread id (`main`, the one thread, `EngineBridge.threads`). `message` and `worker_event` records carry their files' descriptors (`files`: id, name, mime, bytes, sha256), read from the snapshot after the page's records; bytes never ride in records.
5. Requests: the same bridge answers each phone request. `sync_request` gets the window's changes after the phone's cursor, or the window from its start with `reset` when the cursor is absent, zero or stale (`Store.cursorBounds()`); an unreadable store or an unknown thread gets an error page, never silence. `read_state` moves the Mac's read cursor through `Store.markRead` (forward only) and travels back as a record. `task_control` calls `Engine.stopTask`/`retryTask` and replies `task_control_result`; a repeated `requestId` among the last 64 gets its first result again without a run. `search_request` runs `Engine.search` 50 hits at a time. `page_request` answers with the page around a message (`Store.page(around:)`), which never moves the cursor. `attachment_download_request` gets one `attachment_download_chunk` of up to 160 KiB of the stored file (`Engine.attachmentURL`) or of its 512 px JPEG thumbnail (`Thumbnails`, cached in `~/Library/Caches/<bundle id>/thumbs/`), or `attachment-unavailable` when the file is gone or no longer its recorded size; `RelayHost` drops a download chunk for a phone that already has two waiting behind the bucket. `device_remove` is handled by `RelayHost` itself, only for the sender's own key.
6. Size: a page holds at most 200 records and 256 KiB of encoded events (at least one record). An event over 256 KiB goes as a paced chunk set (`RelayHost.pace`); a record too large even for 256 chunks keeps the head of its long text fields plus "…(truncated; the full text is on the Mac)", and a page reply that would not fit becomes an error page.

Events, the handshake, admission checks and catch-up are specified in [ios-relay-contract.md](ios-relay-contract.md).

Phones see every main-timeline message, including acknowledgments and failures, and the history window's topics, work, amendments, worker events and read cursor, which the phone draws as sub-chats and the unread divider (PR C of #313). With `jobs-v1` they also get `job_list`, the job sub-chats' own messages and the job input and controls ([Jobs](#where-job-messages-show)). Protocol 2 (contract 0.7, `version.txt` 0.7.0) is the only one the Mac speaks: a 0.6.x phone gets "Update Yorozu on this iPhone to talk to this Mac." and nothing else. The Mac's relay host keeps its own keys ([Keychain items](setup.md#keychain-items)) and room, never v1's: the relay pins a room to the first key that registers. Registration, heartbeat (ping every 30 s, 10 s pong deadline), redial backoff (2 s doubling to 30 s), frame batching, pacing (every sealed frame charged once against a token bucket of 512 KiB and 30 frames a second; a phone's later frames queue behind its waiting ones; handshake thread lists skip the queue; the queue is dropped when the socket drops and a phone's part on its `hello`, its chunk frames on its new `sync_request`) and device removal, by Mac Settings or by the phone's own `device_remove`, are in `RelayHost.swift`. `deliver()` works per route: relay-route phones get paced batches only while the Mac is registered with the relay, direct-route phones get one frame a message on their link whatever the relay's state, so a phone on the LAN keeps working through a relay outage and `rehandshake()` runs only for relay-route phones. The direct listener restarts after a failure from 2 s, doubling to 60 s; it takes at most 8 connections waiting for a join (24 links in all), closes one without a valid join after 10 s and messages over 1 MiB (4003). While the host runs it holds a `ProcessInfo` activity (`.userInitiatedAllowingIdleSystemSleep`) against App Nap; Keep this Mac awake is a separate setting. A relay that cannot start (locked Keychain, unreadable device file) leaves the Mac app running, shows the error in the pair sheet and is started again every 30 s on the relay URL in force then, until it starts.

Relay replays (bug 1 of #313): the relay buffers phone frames while the Mac is away and deletes one only when the Mac acks its buffer seq. The Mac acks a replayed frame only after the Engine has stored or refused it and every frame before it, or when the frame can never be processed (not a frame, unknown key, malformed, a replayed channel seq, a phone that must update). A phone's last `.compatible` peer-info result is kept in `relay-devices.json` with the host protocol it was computed for, and a `hello` keeps it, so a known phone is served from its first replayed frame after a relaunch. A box from a phone with no result on file is held in memory, unacked (at most 64 a phone); a compatible claim passes the held boxes to the Engine in order, any other result drops them. A box's channel counter is written to disk only after the Engine is done with it, so a quit in between leaves the replay acceptable; the Engine answers a duplicate id with a receipt. Wire details: [ios-relay-contract.md](ios-relay-contract.md#mac-side-seams).

### Marks and the outbox

Every user message carries a delivery mark (#314), forward only: Sending, Delivered, Read, or Not delivered.

- The Mac knows two of them: Delivered once the message is stored (`created`) and Read once routing starts (`readAt`). A user message record goes to phones again when `readAt` is set, through the change sequence.
- The relay answers each phone frame with `accepted` once it has forwarded it to the Mac's live socket or stored it durably (`buffered`), merged on `main` in #332. The phone shows Delivered from `accepted`, from the Mac's `receipt` or from the stored copy, whichever comes first; on a relay without `accepted`, the receipt alone.
- While the Mac is away the phone still sends once joined: the channel keys come from the pairing, so the relay buffers the sealed frame (24 h a frame, 5 MiB a room) and replays it when the Mac registers. The Mac keeps and processes those replays as in [Relay replays](#flow-2-a-phone-message-to-the-same-timeline) above, so a message can be routed (Read) with the phone closed. One stored more than 60 s after its `sentAt` gets the delay line on the Mac and `messageAge` for the secretary.
- The phone's outbox (`Outbox.swift`, one protected file, [setup.md](setup.md#on-the-phone)) holds every message the Mac has not stored, so Send always works and survives a relaunch. Relay join: send the items still Sending. `.paired`: send every item the Mac has not stored; the Mac dedupes by id. An item stops being sent on a `receipt` or its stored copy (never on `accepted`) and is dropped at Read. `admission_status` `rejected` or `expired`, or a deadline that passes before any `accepted`, makes it Not delivered, with Resend (same id, new `ts` and deadline) and Delete. Rules and states: [ios-relay-contract.md](ios-relay-contract.md#the-phones-outbox).
- A message with files (#316) stays Sending, with "waiting for connection" or the upload progress in its details, until the Mac has stored the message and all its files (`receipt` or stored copy); it is never sent to the relay buffer, so the relay's `accepted` never applies to it. An upload that cannot go on (`attachment-corrupt`, `attachment-expired`, an invalid chunk, a local copy gone) makes it Not delivered; Resend uploads again from zero.

## Routing behaviour

The secretary's policy is built by `Engine.routingPolicy` from the `[routing]` hints, read at the start of each route. Bullets marked **(code)** are enforced by the Engine; the rest are prompt policy, which the model may not follow. The decision checks in [Flow 1](#flow-1-a-mac-message-to-a-result) step 4 are code too.

- Greetings, thanks and small talk get a reply and no topic. Other replies and clarifications carry a topic; a `newTopic` on a reply opens or reuses one.
- Substantive thinking, analysis, research, tool use and code are delegated without being asked. Questions about files, calendars or the user's personal notes named by `routing.personal_knowledge` (that clause is dropped when the key is empty), and recall of anything not in the supplied messages or memory, go to a worker ([why](openclaw-integration.md#what-the-agent-sees)).
- Coding work, docs in a repo included, is delegated with an executor the harness offers: the first ready one unless the user names another offered one or its routing notes say otherwise (on OpenClaw `claude`, and `codex` for new coding work that needs an app or a browser unless the user names Claude Code; on Hermes `hermes`). A named tool that is not offered gets one sentence saying so and an offered executor; with none offered, coding work is refused in one sentence ([Harness seam](#harness-seam)). Commit, merge, push, rebuild or restart requests are coding work in the same topic with the executor of the work they continue. Quick shell questions are delegated without an executor (thinking workers have a shell), and so is changing Yorozu's settings ([Settings](#settings)). Coding instructions never ask for tests or CI.
- Operating the Mac or an app on it ("use app X") is delegated without an executor, and the instruction names the apps. Continuing coding work keeps its executor. The user's answer to a question a result asked ("yes, send it") is delegated in that result's topic with the same executor, restating the request as confirmed.
- Topics are broad subjects of one to three words. The topic named by `routing.self_topic` (default "Yorozu") is this app and its repo; the user's own life and preferences go to one separate personal topic.
- **(code)** A message identical to the previous user message, with the same attached files (compared by SHA-256), sent while that message's work is still active, is filed under that work's topic with no reply and no action (`Engine.route`). The same caption with a different file is new work.
- **(code)** `steer` or `retry` aimed at a finished task becomes a new `delegate` in the same topic with the same executor. This redo restates the original instruction (≤ 10,000 bytes, head and tail) followed by "The user now says: …" (the message ≤ 1500 bytes) (`Engine.apply`).
- "Stop" or "cancel that" about running work is `stop` with its task ID.
- **(code)** Routing questions are not failures: a decision with no topic to file under ("Which subject should this belong to?") or a `steer`, `correct`, `retry` or `stop` without a task ID ("Which task do you mean?") is posted as kind `question` with notice code `question_topic` or `question_task`; it stays in the secretary's recent context, since the user's next message may answer it. A `clarify` reply stays `conversation` with notice code `question`; its text is the model's own, so a renderer draws it from the body, not from the code. Other routing errors are `failure`, with their own code or `routing_failed` (`offline` in offline mode).

The repo sentences come from `harness.dev_repo`. The thinking contract says that code changes to the repo at that path belong to a coding worker; the coding contract names it as the main checkout, with its `build/Yorozu.app` and `OWNER_DECISIONS.md`. An empty `dev_repo` turns coding off: the thinking sentence is dropped, every executor reports not ready, the routing policy offers none and tells the secretary to reply that coding is off and can be turned on in Settings › Advanced, a coding decision is refused with "Coding work is off. Choose a repository in Settings › Advanced to turn it on.", and coding work already queued ends before any session is created or anything is sent, with "No repository is set for coding work. Set a repository in Settings › Advanced."

The coding prompt (`Prompts.codingContract`) names the executor and tells the worker: work in its worktree (on Hermes, create `<dev repo>-yorozu-<label slug>-<topicID prefix>` on branch `yorozu/<label slug>-<topicID prefix>` from the base branch first, or keep using it); check compilation with `swift build`; run no tests or CI; commit, merge, push or restart only when the request asks, committing in the worktree (Conventional Commits, signed), merging into the base branch (`dev_base`, `projectx` on the owner's Mac) with `git -C <main checkout> merge --no-edit <branch>`, never force-pushing, and running `<main checkout>/scripts/build_native.sh --restart` as the last step; leave the owner's uncommitted files alone; treat `OWNER_DECISIONS.md` as read-only. It states that it overrides AGENTS.md and CLAUDE.md: no new worktrees (no other worktrees on Hermes), no fetch or pull, no pull requests unless asked. The prompt also carries the task revision, the run marker `[run projectx-code-<uuid>]` (`yorozu-code-<uuid>` on Hermes), the instruction, the user's message verbatim under "The user's message, verbatim:", followed by the work's `Attached document:` lines (from the work's own attachments, never from the secretary's instruction), and the earlier topic conversation: newest first, each message ≤ 2000 bytes (head and tail), ≤ 6000 bytes in all, with "[… N earlier message(s) cut]" in place of anything older. The whole message (on Hermes, contract sent as run instructions plus task) is checked against the harness's `workerGuard` (32000 bytes) before the run handle is stamped; a bigger one fails with an overflow error and no retry offer. Both contracts carry `Prompts.outputRules`: keep tool output short (files read with an offset and limit, long command output through head, tail or grep, `list_windows` and `get_window_state` on the named app rather than whole-desktop views). Both also carry `Prompts.fileRules`: `Attached document` lines name the user's files by absolute path; files made for the user go in the topic's scratch folder, never in a repo checkout or worktree unless the user asks; a standalone `MEDIA:<absolute path>` line in a progress message shows an image in the sub-chat. The coding contract ends: to send files with the reply, end it with a `Files:` line and one `- <absolute path>` line per file.

### Thinking input

A thinking session is sent `WorkerInput.wire`, slim views and never database records: `{policy, topic: {id, label}, revision, instruction, current: {id, body}, history: [{role, body}], memory: [{path, title, attribution, epistemicStatus, body}]}`, followed by the contract.

- History: the topic's `conversation` messages after the request of the latest earlier task in the same topic with the same executor that has a result. Earlier ones are already in the session. Failed or uncertain tasks prove nothing about what the session saw, so their messages are sent again. Messages are added newest first while the whole wire stays within 13000 bytes; older unseen ones that do not fit are replaced by a "[… N earlier message(s) cut]" turn, since the next cutoff passes them.
- Memory: search hits on the request and the instruction, up to 3000 bytes.
- Files: one `Attached document: <path>` line per file the work carries follows the wire (and a follow-up turn's amendments), outside the 13000-byte history bound; a file deleted since it was attached gets "Attached document no longer available: <name> (deleted since it was attached)". Images may also ride on the first step as `agent` `attachments` ([Attachments](#attachments)).
- The whole step message is checked against the harness's `workerGuard` (32000 bytes) before the run ID is stamped, so an oversized one fails the work rather than leaving it uncertain. Hermes sends the contract as the run's instructions on every step and counts it in.
- A follow-up turn of the same task sends only the new amendments, under "Follow-up turn of the same task, now revision N. The user changed the request:", and asks for the whole answer again.
- The contract carries `Prompts.outputRules` (short tool output), the file rules and the cua rules, and allows `"files"` (absolute paths) in the final JSON.

The coding poll gives up as `uncertain` after about 10 minutes of Gateway failures, 15 unreadable histories in a row, or 3 polls that find no active run.

### Context overflow and compaction

Gateway calls and messages are in [openclaw-integration.md](openclaw-integration.md#compaction).

Hermes compacts its own sessions at the same threshold, set in its profile; Yorozu detects the rotation and notes it ([hermes-integration.md](hermes-integration.md#compaction)). The rest of this section is OpenClaw.

- Thinking: before each task, the topic session's token count is read; at half of min(its context window, 258,400) tokens the session is compacted as its own call. A compaction posts a sub-chat event of kind `compaction` ("Compacted this topic's session: N → M tokens"). A failed one posts a short `failure` message to the main timeline (a `StreamUpdate.notice`), and the task continues.
- Thinking overflow (`context_overflow` or `compaction_failure` on a step): one forced compaction, then the task fails with `ProjectError.overflow`, saying either that asking again should now work or to start a new topic.
- Coding: a compaction by Claude Code or Codex (new session id, or a lower fresh token count after the run) posts a `compaction` event. An overflow fails the task with "<tool>'s session ran out of context", the worktree changes kept, and says to start a new topic.
- An overflow failure is posted as is, without "Say retry to try again.": a plain retry would hit the same limit.

## Attachments

Files of any type in both directions (#316): the user attaches them in either composer, workers get them as paths (images also as model input), and workers can return files with their results or share images in the sub-chat. Limits everywhere: at most 10 files a message or result, each at most 50 MB (50,000,000 bytes; `FileStore.maxFiles`, `maxBytes`, matching the wire's `MessageAttachment`). The phone's transfers are in [Flow 2](#flow-2-a-phone-message-to-the-same-timeline) and [ios-relay-contract.md](ios-relay-contract.md#attachments).

- File store (`FileStore`): `~/Yorozu/files/<YYYY-MM>/<YYYY-MM-DD_HHMMSS>_<name>` in the Mac's local time, `_2`, `_3`… before the extension on a clash; `<data root>/files/` under `PROJECTX_DATA` and in fixture mode ([setup.md](setup.md#where-data-lives)). Names lose `/`, `:` and control characters, keep Unicode and are cut to fit APFS's 255 bytes (a long extension counts as name). Directories 0700, files 0600. A root that resolves inside a git checkout or worktree (any ancestor holding `.git`) is refused: that launch has no file store, sending a file is refused ("Attachments can't be stored here.") and the status line says "Attachments are off: …". Files are kept until the user deletes them in Finder; Yorozu never deletes a stored file except a copy no row took.
- Schema (`attachments-r1`): `attachments` (id, `messageID` or `eventID`, path relative to the root, name, mime, bytes, sha256, created) and `workAttachments` (work id → attachment id, in link order). `Snapshot.attachments` and `Snapshot.workFiles` load them. `Engine.attachmentURL(_:)` gives a stored file's URL, nil once it is gone.
- Work carries its files: `delegate` links the source message's files plus those carried from earlier work: the original work's on retry, redo and correct (a correction also links the mistaken work's files to intended work it steers). A steer or amendment links its message's files to the work (`Store.amend`, `deferCorrection`) and appends their `Attached document:` lines to the amendment text, so a live steer and a follow-up turn both get them; a follow-up turn re-reads the work's files. A retry therefore never loses a file, and a file deleted since gets the "no longer available" line.
- Into workers: the lines are added by `Prompts.workerMessage` (thinking) and `Prompts.codingTask` (coding), never taken from the secretary's instruction. On OpenClaw, images also go as `agent` `attachments` (`OpenClawHarness.inlineImages`) when `models.list` lists `image` in the worker model's `input`, the image is PNG, JPEG, GIF or WebP of at most 6 MiB, and the encoded params fit the transport ([openclaw-integration.md](openclaw-integration.md#attachments-and-media)); otherwise the path alone. Memory steps send none. Hermes gets paths only ([hermes-integration.md](hermes-integration.md#workers)).
- Returned files: `Prompts.withFiles` collects the thinking JSON's `files`, `MEDIA:<path>` lines inside or outside the JSON, the payload `mediaUrl`/`mediaUrls` (OpenClaw) and, for coding replies, a `Files:` section of absolute or `~/` paths; `file:` URLs and `~/` resolve, a relative path in a coding reply resolves against its worktree, remote URLs stay text. `MEDIA:` lines and the `Files:` section leave the stored text ("See the attached file." when nothing else is left). `Engine.finish` copies each file in (`FileStore.adopt`: any readable path except private folders such as `~/.ssh`, `~/.gnupg`, keychains, credential folders, Yorozu's own data, and key-like names; a prompt-injected worker could otherwise name a secret that then syncs to the phone; files the user attaches are not filtered); one past the 10th, over 50 MB, missing or unreadable is skipped with a one-line note at the end of the result. The copies are attached in `Store.finish`'s transaction to the result, the `superseded_result` event of a follow-up turn, or the unconfirmed-change notice; copies no row took are removed. Reconcile (OpenClaw, Hermes) parses replies the same way, so a result delivered after a restart keeps its files.
- Sub-chat images (open question 6): a standalone `MEDIA:<absolute path>` line naming an image in a worker's progress message (kind `message`) leaves the event body ("Shared an image." when nothing else is left) and becomes `StreamUpdate.media` (`Prompts.emitProgress`). The Engine copies up to 10 images and attaches them to that event (`Store.attach`), re-stamping its `seq` so phones get it again; an event that was never stored (withheld as sensitive) drops them. The coding poll sends an event's images once. The Mac has no sub-chat UI, so these show only on the phone.
- Scratch folder (open question 4): the contracts tell workers to write files they make for the user in `$TMPDIR/yorozu-scratch/<topic id>/` (the app's temporary folder, `Prompts.scratchDirectory`), which a Codex `workspace` sandbox can write too; nothing there needs to last.
- Secretary and memory: the secretary gets descriptors only ([Flow 1](#flow-1-a-mac-message-to-a-result) step 2). Extraction gets the source message's files as name and path lines, never contents ([Memory](#memory)).

## MCP servers and computer use

Yorozu declares which MCP servers its workers may use; the harness starts, connects and calls them, and Yorozu never runs a server or a tool call itself. The list workers get is `Config.effectiveMCPServers`: `[mcp_servers]` in `config.toml` ([setup.md](setup.md#mcp-servers)) plus the servers of enabled integrations, deduped by name with `[mcp_servers]` winning; a server name that a disabled integration declares is dropped from `[mcp_servers]` too, so switching cua off removes cua-driver even from a file that lists it there. `OpenClawHarness` mirrors it into OpenClaw as `yorozu-<name>` servers that only Yorozu's sessions switch on, and mirrors it again when a reload changes it ([openclaw-integration.md](openclaw-integration.md#mcp-servers)). A list that cannot be mirrored fails each worker run with the reason until the next attempt succeeds. On Hermes the list is written into the `yorozu-worker` profile's `mcp_servers` by the profile setup, so it is profile-wide rather than per session ([hermes-integration.md](hermes-integration.md#profiles)).

Integrations are data, never loaded code (`Integration.swift`): a name, a title, an on/off switch, MCP servers, worker rules with a `{session}` placeholder for the per-run cua session label (and optional YOLO variant), read-only checks (file, unix socket, or a built-in command marked read-only, run without a shell with a 5 s timeout by `Integration.Check.run`, only when the app asks), fixes (copy a command or open a URL) and settings. Built-ins ship with the app; the user's own are `[integrations.<name>]` in `config.toml` and may declare only file and socket checks. `Prompts.integrationRules` puts the rules of enabled integrations in both worker contracts.

Computer use goes through the built-in `cua` integration and its cua-driver server ([cua-integration.md](cua-integration.md)), on by default (`[integrations.cua] enabled`). Its rules are prompt policy in both the thinking and the coding contract (only the named apps, one window at a time, background delivery, a fresh cua session per run, fresh snapshot then verify, no blind retries, never taking focus (neither approval nor YOLO lifts it), ask before outward-facing steps and the listed risky tools, no secrets, screenshots shared only as `MEDIA:` lines in progress messages, no accessibility-tree dumps or clipboard contents in progress or results, never screen content in memory). Nothing in code enforces them.

Workers treat the Mac as unattended, whichever device the request came from (owner decision): no `bring_to_front`, foreground delivery, focus-taking shortcuts or `open` without `-g`, and no approval or YOLO mode lifts this. An app that accepts only foreground input is reported as not doable in the background, and the worker stops.

YOLO mode (`general.yolo`, off by default) swaps the ask-first sentence of the cua rules (`Integration.cua.yoloRules`) for one that says to do the outward-facing steps the request asks for in an app (sending, posting, purchasing, deleting, submitting) and to use the risky tools (`kill_app`, `clipboard_write`, `set_config`, `replay_trajectory`, `start_recording`, `install_ffmpeg`, `browser_download`, `browser_set_input_files`) when the task needs them, without asking. Both contracts get it from the next task. What always holds: asking before changing settings or credentials and before any step the request did not ask for, no secrets or password fields, never taking focus, and never reading or messaging other agents' sessions. `yolo` is itself security-relevant, so a worker asks before turning it on.

## Settings

`config.toml` in the data root holds every setting; keys, defaults, precedence and when each applies are in [setup.md](setup.md#settings-configtoml).

- Launch: `AppModel.start` loads the file (writing the defaults when it is missing; an invalid or unreadable one is left as is, posts `config_invalid` and that run uses the code defaults), applies `PROJECTX_*` overrides (`ResolvedSettings`) and keeps the result twice: `launched`, whose harness kind, agent, transport, Gateway URL and Hermes URL stay fixed for the run, and `resolved`, which reloads replace. It then starts the harness, waits up to 10 s for the first model metadata read before resuming queued work, applies keep-awake and the login item, and starts `ConfigWatcher` from the file text it loaded.
- `SettingsBox`: the harness and the Engine get a closure over it instead of fixed values (`HarnessSettings`: role models, MCP list, YOLO, `dev_repo`, the `config.toml` path, routing hints) and read it at the start of each route, task or extraction, so a reload applies from the next one without rebuilding either. Before a message from the Mac or a phone is handed to the Engine, the app waits for any metadata read in flight and, while none has succeeded, starts another at most every 30 s.
- Reload: a valid file replaces `resolved` and the box at once (explicit models, YOLO, routing hints, MCP list), then the model metadata is read again and the automatic models follow. It also posts `settings_changed` for changed security-relevant keys, restarts `RelayHost` on a new relay URL (live mode; restarts run one after another, each on the URL in force once the old host stopped), or, on a changed `[direct]` alone, restarts or stops the direct listener and closes its links (`RelayHost.setDirect`), switches keep-awake, appearance and the login item to the settings in force once its awaits finish (so an older reload never undoes a newer one), and puts "Relaunch Yorozu to apply: …" in the status line for launch-fixed keys. An invalid or missing file keeps the last valid settings and posts `config_invalid` once per distinct problem.
- Settings window: each change is a read-modify-write of the file (`Config.update`) applied through the same reload at once ([Mac UI](#mac-ui)).
- Self-configuration: the secretary routes "change a setting" as delegate without executor. The thinking contract names the `config.toml` path, says the file documents its keys, and has the worker change MCP servers, the relay URL, direct connection, the harness, Advanced items or `yolo` only after the user's explicit yes in the chat (prompt policy, not code). The worker edits the file, the watcher reloads it, and a security-relevant change shows up as a "Settings changed: …" notice.

## Setup and readiness

First setup and the "can Yorozu answer" state (#317). The user-facing steps, the CLI and its JSON are in [setup.md](setup.md#first-setup); OpenClaw's checks and write in [openclaw-integration.md](openclaw-integration.md#assisted-setup).

- Step engine (`SetupEngine`, `Setup.swift`): one engine behind the setup window and `Yorozu setup`. Steps in order: `welcome`, `harness`, `gateway`, `models`, `integrations`, `yolo`, `start_at_login`, `pair_iphone`, `path_link`, `done`. Each `SetupStep` has an id, a title, a state (`done`, `needed`, or `app` when only the running app can finish it), its checks as readiness items, an optional question (id, text, choices, default) and, for the assisted OpenClaw write, the `OpenClawPlan` the user is shown. `evaluate()` runs the read-only checks and derives each state from them and from `config.toml` (`[setup] answered`), so a step whose checks pass is done without asking. `answer(id, value)` applies one answer (a `Config.update`, the assisted write, or the `~/.local/bin/yorozu` link) and evaluates again; when every step is done it sets `[setup] done`. The app passes a `Host` (native enrollment, a paired phone) and its own `GatewayRPC`; without a `Host`, the steps `gateway`, `start_at_login` and `pair_iphone` are app-only and report where to finish them.
- Readiness model (`Readiness`, `Readiness.swift`): items with a stable id (`openclaw.gateway`), a plain-language title, the raw detail for Details, a severity (`ok`, `warning`, `blocking`) and an optional fix: open a setup step, copy a command or open a URL; Yorozu never runs a fix. The state is Ready, "N items need attention" (warnings), or Blocked: only when no harness is installed at all, or when `[harness] agent` is OpenClaw's default agent (workers never run on the user's personal agent); a missing main harness while another is installed is a warning that points to the harness step. `Readiness.harness` is the main harness's detection plus Gateway `health`, which the app runs at launch and again after a Gateway call fails; integration checks run only during setup, while Settings › Advanced shows and on Check again, never on a timer. The app maps it to the wire's `ReadinessData` for phones ([ios-relay-contract.md](ios-relay-contract.md#readiness-mac---phone-can-the-mac-answer)).
- Harness detection seam (`HarnessSetup`, beside `Harness`): each adapter declares `installed` (a local file check, cheap enough to run for every adapter), `detect()` (installed, version and reachable, as readiness items with fixes), the setup steps it takes part in, and its coding executors for display (`CodingExecutor`: whether the tool's binary is found on the launch `PATH`, `~/.local/bin` or the Homebrew folders; never a login state, which no Gateway method reports). `OpenClawSetup` also inspects Yorozu's own entry, the role models and provider auth, and builds and applies the assisted `config.patch`. `HermesSetup` wraps Hermes's read-only readiness, adds the default profile's API server (a command to copy) and the profiles' staleness, and the harness step offers the profile write (`hermes_setup`, [hermes-integration.md](hermes-integration.md#setup-step)). `Config.HarnessKind.adapter` picks one.
- Integrations as data: see [MCP servers and computer use](#mcp-servers-and-computer-use).
- Plain-language errors (`PlainError`): known setup failures to a cause id and a sentence for notices, the status line and readiness items ([openclaw-integration.md](openclaw-integration.md#plain-language-errors)).
- CLI entry point: the binary's `@main` is `enum Main` in `SetupCLI.swift`. With `setup` as the first argument it runs `SetupCLI` on a detached task and exits with its code; otherwise it starts the SwiftUI app (`ProjectXApp.main()`). The CLI opens no window, shows no Dock icon, takes no `app.lock` and never opens the Store, so it runs beside the app on the same data root; its `config.toml` writes are atomic and the app's watcher applies them.
- App side (the menu-bar host): the setup window opens at launch until `[setup] done` and from Settings › General › Run Setup Again…, next to a status row ("Ready" or "N items need attention"). The readiness state replaces the popover's fixed harness line: when Blocked the composer is off and shows the reason with "Fix…"; warnings show a banner with "Fix…"; "Fix…" opens the setup window at the item's step, or at the harness step for an item with a command or link (copy and open buttons are in the window). Phones get the same readiness, titles included: Core builds them with `String(localized:)`, so they are in the Mac user's language ([Mac UI](#mac-ui)).

## Jobs

Scheduled jobs (#319). Yorozu runs them itself, never through the system `cron`, launchd, OpenClaw automations or Hermes cron. Each job has its own topic, so its sub-chat and worker session carry from run to run. A job is a script, an AI step (`instruction`), or a script whose output feeds an AI step. Jobs are made and changed by asking in the chat or by editing the file; the Jobs lists in Mac Settings ([Settings › Jobs](#settings--jobs)) and on the phone ([Phone Jobs screen](#phone-jobs-screen)) show them with Pause/Resume, Run now, Delete and each job's sub-chat with its own input. The phone side travels as capability `jobs-v1` ([ios-relay-contract.md](ios-relay-contract.md#jobs)).

### `jobs.toml`

The file sits next to `config.toml` in the data root ([setup.md](setup.md#where-data-lives)), one `[jobs.<id>]` table per job (`JobsFile.swift`, `JobSpec` in `Jobs.swift`).

| Key | Default | Meaning |
|---|---|---|
| `<id>` | | `^[a-z0-9][a-z0-9-]{0,39}$`; also names the job folder `<jobs root>/<id>/` |
| `name` | required | Non-empty; the topic label and the header of posted results |
| `schedule` | required | A non-empty list of 5-field cron strings in the Mac's time zone; a slot fires when any matches |
| `post` | `"always"` | `"always"` or `"notable"` ([Posting](#posting)) |
| `once` | `false` | Run at the next slot, then retire |
| `paused` | `false` | No scheduled slots fire; Run now still works |
| `retired` | `false` | Set by Yorozu after a one-shot runs; never fires |
| `script` | | Shell text, run by `/bin/zsh` in the job folder |
| `instruction` | | The AI step |
| `ai_when` | `"always"` | Gate before the AI step: `"always"`, `"changed"` or a regular expression |
| `timeout` | `600` | Script timeout in whole seconds, 1–86400 |
| `model`, `executor` | | Run the AI step on this model or executor (see below for what applies) |
| `topic` | | The job's topic id; a worker that creates the job writes its own task's topic |

Validation: unknown keys anywhere are errors; a job needs a non-blank `script` or `instruction` (or both); every cron string must parse; `ai_when` must be one of the two words or compile as an `NSRegularExpression`; `model`, `executor` and `topic` must be non-empty when present. A missing file means no jobs. Jobs keep their file order.

Writes go through `JobsFile.write`: the whole file in one canonical layout with a commented header that documents the keys (hand-written comments are not kept), defaults and unset keys left out, multi-line scripts as `'''` literal blocks, duplicate ids and invalid jobs refused, temporary file, fsync, rename, mode 0600. `JobsFile.update` is read-modify-write under a lock, so an edit made since the last load survives; the controls and one-shot retirement use it.

`JobsWatcher` watches the folder with FSEvents, so in-place edits and atomic saves are both seen, debounces 300 ms and ignores unchanged bytes. Each report carries the last valid set and the problem, if any: an invalid file keeps the previous set running. The app reports one notice per distinct problem, code `config_invalid` (params `file`, `line`, `key`, `reason`): "Jobs not updated: … The last valid jobs keep running until the file is fixed." When the problem's key names one job that already has a topic, it is a `job_note` in that job's sub-chat (param `job`); otherwise a `failure` in the main timeline.

### Cron evaluator

`CronExpression` (`Cron.swift`) is Yorozu's own: minute (0–59), hour (0–23), day of month (1–31), month (1–12), day of week (0–7, 0 and 7 are Sunday). A field is `*` or a comma list of `n`, `a-b`, `*/s`, `a-b/s` or `a/s` (from `a` to the field's end). Names (`mon`, `jan`) and `@daily`-style macros are refused. When both day fields are restricted, a day matches either (POSIX); a day field that starts with `*` (such as `*/2`) counts as unrestricted (Vixie cron). With an unrestricted day of week, a day of month that never occurs in the listed months (`0 0 30 2 *`) is refused. Intervals one line cannot express, such as every 90 minutes, are several lines in `schedule`.

`next(after:)` returns the first matching minute strictly after a date, in the Gregorian calendar of the Mac's current time zone (`Cron.calendar()`), searching about 5 years ahead. Daylight saving: a local time the change skips is skipped; a local time that repeats matches once, at its first occurrence.

### Scheduler

`JobScheduler` (an actor) holds the last valid set and sleeps until the earliest next fire of the jobs that are neither paused nor retired.

- Re-arm: on every new set, and through `rearm(clockChanged:)`, which `JobsWiring.swift` calls on `NSWorkspace.didWakeNotification`, `NSSystemClockDidChange` and `NSSystemTimeZoneDidChange` (after `NSTimeZone.resetSystemTimeZone()`, so slots stay at the same local time in the new zone). A clock change pulls every job's last slot back to now at most, so a slot "fired" in a future the clock left counts again from now.
- Each job remembers its last slot, fired or skipped. A new job, or one whose schedule, pause or retirement changed, counts from that moment: no slot before it fires.
- Late slots (open question 8): a slot reached more than 60 s late (asleep, app not running) is skipped silently and the next one counts from now. There is no catch-up.
- Overlap is the Engine's rule (`runJob`, [Run flow](#run-flow)).
- One-shots: once `runJob` reports a run started, the scheduler sets `retired = true` through `JobsFile.update` and keeps the job retired in memory until the file says so, writing again on later sets. A slot that does not start a run (skipped for approval or overlap) does not retire it. The write is best effort: an invalid file refuses it until the next valid set.
- `stop()` is final: nothing fires after it.
- `nextRuns` gives the next fire per job for the Jobs lists (Settings › Jobs and `job_list`).

The app starts jobs after `engine.resume()` in every run mode (open question 16): fixture mode runs them with scripted AI replies, and offline mode loads and lists them but `runJob` runs nothing (skip reason `unavailable`).

### Run flow

`Engine.runJob(spec, slot:, manual:)` handles a slot, Run now (`manual`, which also runs a paused or retired job) and the retry of a script.

1. The Engine's current definition of the job runs: a caller's copy that differs from it (the scheduler holding an older set) skips the slot as `unavailable`, with no note. Skip checks, in order: offline mode (`unavailable`); paused or retired and not manual (`paused`); the job already inside `runJob` (`overlap`). Then the data directory is bound to the run mode as on a send (a mismatch skips as `unavailable`), the job's topic is bound and its runs and open topic work read: a run or a script step left `uncertain` skips the slot as `uncertain` (open question 9); a `running` run, or open work of the AI step's executor in the topic (an answer to the job's input included), skips it as `overlap`. These two post a `job_note` "Skipped the run at <slot>: …" (notice `job_skipped`, params `job`, `name`, `reason`, `slot`), at most one per streak: a note is not repeated while the topic's last message is a note with the same reason. A job with a script then needs the script runner (`unavailable` without it) and an approval of the script's exact hash (`needsApproval`, no note: the approval request is the notice).
2. The trigger: a `system` message of kind `job_run` in the job's topic ("Scheduled run of “<name>” for <slot>." or "Run now …"). The main timeline, phones, the secretary and memory extraction never see it. The run's steps are `work` rows on it, which satisfies `work.messageID`.
3. A `jobRuns` row in state `running`; the rest runs in a task the Engine keeps per run.
4. Script step: a `work` row with executor `script` (instruction "Run the job's script:" plus the script, ≤ 6000 bytes), started at once. The Engine runs it itself through `ScriptRunner`, outside the model lanes and with no harness. A run ID `script-<id>` is stamped just before the spawn, so from then on a quit leaves the work `uncertain` and it is never queued again. The step ends `done` or `failed` (`Store.endScript`), or `cancelled` when a stop suppressed it meanwhile. A lifecycle event records the summary ("Exit code 0.", "Timed out; stopped.", "Couldn't start the script: …", "Ended by a signal.") and the log path, and the run gets the exit code and output hash. A failed script ends the run ([Posting](#posting)).
5. Gate (open question 4): the AI step runs when the job has no script, `ai_when` is `always`, it is `changed` and the output hash differs from the job's previous run with one, or the regular expression matches stdout (its first 1 MiB). With no instruction, or a closed gate, the run ends after the script.
6. AI step: a `work` row in the job topic on the same trigger, instruction = the job's `instruction`, "Scheduled run for <slot>." (or "Run now"), and for script → AI jobs the log path plus a head-and-tail excerpt of the log (≤ 6000 bytes; a secret-shaped excerpt is left out with a note), all cut to 10,000 bytes. It runs on the topic's thinking worker, in the topic's session (same session key scheme, so the session guard still holds), or on the job's `executor` when the harness offers it ready. `model` is parsed and validated but not applied yet: the AI step uses the role's model. The step joins the normal lanes (2 thinking, 1 coding) but is marked as job work: `pump` starts work the user sent first, and job work does not count toward the 32-item send cap (open question 10).

Job agent rules (`Prompts.jobRules`): every task in a job's topic, scheduled or typed, gets in its worker policy the job's name and id, the path of `jobs.toml` and its own entry as JSON, and the rules: edit only that entry and keep the file valid, never touch other jobs; ask whether results always go to the main chat or only when notable before setting `post`; never say a script change is active before the user's yes to Yorozu's approval request; the Mac is unattended (never wait for input, take focus or start anything interactive). On a scheduled or Run-now run the final JSON also carries `"notable": bool` (true when the result needs the user's attention, asks something or something failed); `WorkerOutput.notable` reads it; a coding executor's free-text answer (OpenClaw and Hermes) is notable when it carries `"notable": true`, else not. The thinking contract, in every topic, names `jobs.toml`, its keys and rules, and says that a new job's entry takes `topic` = the creating task's topic id.

### Script runner

`ScriptRunner` (`ScriptRunner.swift`) runs a job script as a child process of the app:

- `posix_spawn` of `/bin/zsh -f -c <script>`: `-f` skips `~/.zshenv` and the other startup files, so the environment is exactly the one given. Standard input is `/dev/null`; the working directory is the job folder.
- Environment (open question 6), nothing else: `HOME`, `USER`, `LANG` (the app's, else `en_US.UTF-8`), `TZ` (the current zone id), `YOROZU_JOB`, `YOROZU_JOB_DIR` and `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`. No `PROJECTX_*` variable or app secret reaches a script.
- Its own process group (pgid = pid), no inherited descriptors, default signal handling and an empty signal mask.
- Folders: `<jobs root>/<id>/` and its `runs/` are created mode 0700. Each run's full output, both streams in arrival order, goes to `runs/<timestamp>-<work id prefix>.log`, mode 0600.
- Output: both pipes feed the log and the hashes in arrival order, and one ordered stream into the sub-chat. Chunks become `output` (stdout) and `error` (stderr) worker events, cut only at whole UTF-8 characters and never tail-cut; a chunk that looks like a secret, screened together with the last 256 characters of its stream so a secret split across chunks is caught, is shown as "[Output withheld from the chat: it looks like a secret. The run log has it.]". The sub-chat gets the first 2 MB of a run's output, then a lifecycle line "[The chat stops here at 2 MB of output; the output continues in the log.]"; the log keeps everything, and only the sub-chat part is buffered.
- Output hash: SHA-256 (hex) of the hex SHA-256 of stdout followed by that of stderr, so the interleaving of the two pipes never changes it. The first 1 MiB of stdout is kept for `ai_when`.
- End: the leader's exit ends the run, not the pipes' end. The leader is awaited with `waitid(WNOWAIT)`, so it stays an unreaped zombie (its pid, the group id, cannot be reused) while the group is SIGKILLed; then it is reaped. The pipe readers then get 2 s to drain; one still blocked (a child that left the group, for example with `setsid`, holds a pipe) is abandoned, and that child keeps running. Background children still in the group are killed with it.
- Timeout: SIGTERM to the process group after `timeout` seconds, SIGKILL 5 s later if its leader is still there. It counts as a timeout only when it fired before the leader exited. Signals go to the group only while its leader is unreaped.
- Stop: the same SIGTERM and SIGKILL grace; `stop(work:)` returns once the leader is gone, so the reply is "Stopped." only then ("Stopping it; not confirmed yet." if it is still there).
- Quit: `terminateAll()` marks the runner as quitting, sends SIGTERM to every running group, waits up to 2 s, then SIGKILLs what is left. It is synchronous and runs from `AppModel.stop()` and `Engine.shutdown()`. A run that ends while quitting throws `CancellationError`, and the Engine leaves its work and run untouched, so the next launch reports it interrupted ([Restart](#restart)), never failed.

### Approval gate

Open question 1. A script runs only under an approval of its exact SHA-256 (`sha256Hex` of the script text). YOLO never lifts this.

- Every load of the file (`Engine.jobs`) and every run checks each non-retired job: a script whose hash differs from `jobs.approvedScriptSHA` gets a pending `jobApprovals` row (`Store.requireApproval`) and, when new, an `approval_request` message in the job's topic, which shows in both the main timeline and the sub-chat: "“<name>” has a new (or changed) script that needs your yes before it runs; YOLO doesn't lift this.", the script in a code fence one backtick longer than any backtick run in it, so the script cannot close it (≤ 3000 bytes, else a head-and-tail excerpt and "The full script is in jobs.toml."), "Say yes to approve this exact script." (notice `job_approval_requested`, param `approvalID`). A further change supersedes the pending request and makes a new one; a removed script supersedes it.
- Approvals are recorded by Yorozu only (`Store.approve`), never by a worker: only for a user message created after the request, only while the request is still the job's pending one, and only while the job's current script still has the requested hash. Otherwise nothing is approved; a changed hash posts "That script changed after the request, so it was not approved…" (`job_approval_stale`) and a new request follows.
- `approve` action: pending approvals go to the secretary as data (`RoutingInput.approvals`, `{approvalID, topicID, job}`), and the routing contract then allows `action: "approve"` with an `approvalID` and no other key, only for a message that clearly approves that script. `validate` accepts it only for an approval in the input. `apply` files the message in the job's topic and records it; the acknowledgment is "Approved. “<name>” runs this script from its next run." (`job_approved`). A request for a deleted job lapses: it is not offered.
- Job input: while the job has a pending approval, a message typed in its own input gets one raw secretary-model check (`Prompts.jobApprovalCheckPolicy`, through the routing contract); `approve` for that approval records it. The job's agent still answers the message.
- The fixture harness approves the first pending approval on the message "yes".
- The limit: workers run at full permission with a shell, so this gate is not a sandbox. It stops unattended scheduled runs of code the user has not seen; it does not stop a worker that runs the same commands itself.
- The hash covers only the inline `script` text. Helper files in the job folder that the script calls (or anything else it reads) are not covered: changing them needs no new yes.
- A job with only an `instruction` needs no approval: it runs an agent, which has a shell, on its schedule without the user's yes.

### Posting

`Store.finish` takes a `delivery` (the result kind) for work in a job topic, decided by the request's kind:

- An AI step (trigger `job_run`) posts a `result` to the main timeline (the answer alone, replying to the trigger; the Mac heads it with the job topic's label, phones from 0.7 likewise) when the job posts `always` or the answer has `notable: true`; otherwise a `job_result` that stays in the sub-chat.
- A script-only run (or a closed gate) posts, replying to the trigger, a head-and-tail excerpt of the log (≤ 4000 bytes; "Ran; no output." when empty; a secret-shaped output stays in the log and the message gives its path). Notable (open question 3) means the output hash differs from the previous run's; it is a `result` when the job posts `always` or the run is notable, else a `job_result`.
- Failures always post, in both modes, a `failure` in the job's topic that shows in the main timeline (notice `job_failed`, params `reason` `exit`, `timeout`, `launch` or `ai`, and `error`): "“<name>” failed: its script ran past its N-second limit and was stopped. Its output is in the job's chat.", "… its script ended with an error (Exit code 2.) …" or "“<name>” failed: <error>". Failed runs count as notable. A failed AI step posts the usual task failure.
- The full output of every run stays in the sub-chat: worker events, the lifecycle line and any `job_result`.
- Only messages posted to the main timeline go to memory extraction (open question 11): extraction takes `conversation` and `result` only.
- The run records `notable` and `posted`.

### Routing and the job input

- `RoutingInput.jobs`: each non-retired job with a topic as `{topicID, name, summary}` (name ≤ 120 bytes, the summary's first line ≤ 160 bytes). The trim drops jobs, last listed first, after the less active topics down to 10 and before recent messages, counting them in `omitted` ("N jobs omitted"); approvals are never dropped. Empty lists are left out of the JSON, so a workspace without jobs sends the same context as before.
- Policy: a request for a new scheduled or recurring job is delegate without executor with `newTopic` set to the job's short name (always in the policy). When jobs or approvals exist, the policy adds that a message about an existing job (what it does or found, changing, pausing, resuming, running now, deleting) is delegate without executor in that job's topic, and the `approve` rule. A worker in that topic then edits `jobs.toml`.
- Topic binding (open question 2): `jobs.topicID` is the binding. An entry's `topic` that names an existing topic binds (or moves) it there, unless another job holds that topic: then it is ignored (one topic per job, a unique index on `jobs.topicID`); an entry without one keeps its earlier binding or gets a new topic named after the job. A job topic is any topic bound in `jobs`; a deleted job's binding stays.
- `latestTopic` and the verbatim-resend check look only at main-timeline `conversation` messages, so the job input never moves them.
- `Engine.sendToJob(jobID:body:id:)`: the job input. The body must be 1–6000 UTF-8 bytes; text only, no files. Callers: the Settings › Jobs detail pane and a phone `message` with `jobId`, which passes its id and send time (`sentAt`). It stores a user message of kind `job_input` in the job's topic and delegates it there without the secretary, with no `routing` receipt, instruction "The user wrote this in this job's own chat. Answer them as the job's agent, in their language." on the job's AI executor. While the job's run or an earlier answer is active, the message waits and runs as the next turn in the same session (open question 12): `drainJobInput` takes the oldest unanswered one when the run or the work ends, and once per job topic after every load of the set and after `resume`, and stamps its `readAt` as it hands it to the job's agent (the Read mark, #314). Like a send, it first binds the data directory to the run mode. The answer is a `job_result` in the sub-chat. Thinking history includes `conversation` and `job_input` messages of the topic.

### Controls and summaries

- `pauseJob`, `resumeJob` and `deleteJob` edit `jobs.toml` through `JobsFile.update`; the watcher then hands the new set to the Engine and the scheduler. `deleteJob` removes the entry only (open question 13): the topic, its history, the `jobs` binding and the job folder stay. `runJobNow` runs the current spec under the no-overlap rule, paused or not. Without the writer (before `configureJobs`) they refuse with "Jobs can't be changed here yet."
- Stop and retry: `stop` on a script step ends its process group and settles it locally as stopped once the group's leader is gone (after the SIGKILL grace at most); there is no harness call. `retry` of a failed or uncertain script step retires it and starts a new run of its job (Run now), reporting a skip as "It didn't run again: …" (`job_skipped`); a deleted job's script cannot be retried. AI steps stop and retry like other work. After each, the run's state is recomputed from its steps.
- Summaries (open question 15): stored in `jobs.summary`, keyed by `jobs.specSHA`, the SHA-256 of the spec as sorted-key JSON. On every load a job whose hash changed gets one raw secretary-model run (`Prompts.jobSummaryPolicy`, through the routing contract): line 1 when it runs in plain words in local time, then what it does and how it posts, no ids or cron syntax, ≤ 400 characters, in the job's language. When that run is unavailable (fixture, offline, an error), a plain fallback names the cron strings. The next run is computed exactly by the scheduler, never taken from the summary.
- `Engine.jobStatus(nextRuns:)` builds the rows of both Jobs lists, one per job of the current set in file order: name, topic, summary, next run, last run (the latest run's start) and result (`uncertain` when the latest run is, else the last finished run's state, with its `notable`), and state, first match wins: `running` (the latest run), `needsAttention` (the latest run is uncertain), `needsApproval`, `finished` (a one-shot that ran, `retired`), `paused`, else `idle`.

### Settings › Jobs

`JobsSettings` (`SettingsJobs.swift`), a tab of the Settings window between Storage and Advanced; open question 14 makes it the Mac's job sub-chat.

- Rows (`JobRow`) from `Engine.jobStatus` with the scheduler's `nextRuns`: the name; the schedule in words (the summary's first line, else the cron strings joined until a summary exists); the state (Running, Paused, Needs approval, Needs attention; none when idle); "Next: <time>" or "No next run"; "Last: <result> · <time>" (Done, Failed, Stopped, Interrupted, Running). Times show the date when not today. The list refreshes on every snapshot, on every new valid set (`AppModel.jobSpecs`, set by `JobsWiring` after the Engine and the scheduler take it) and every 30 s while the tab shows.
- Actions, in each row's context menu and in the detail pane: Pause or Resume, Run Now, Delete… with a confirmation ("… is removed from jobs.toml and won't run again. Its chat and its folder stay."). A refusal or a skipped Run Now ("Didn't run." and the skip reason) shows in the detail pane.
- Detail pane (`JobDetail`, the selected job, the first by default): name, schedule and actions; then the job's sub-chat, its topic's messages (job-only kinds included; a `job_run` trigger is a compact system row with a clock icon) and its work's worker events interleaved by time as compact monospaced rows (a script's output, stderr in amber), with day separators; then the job input. The input is text only, with the main composer's field, send key and 6,000-byte limit, enabled only while the app is ready and the run mode takes input; it calls `Engine.sendToJob`.
- No jobs: an empty state with an example request and Show jobs.toml (its folder when the file does not exist yet).
- Layout: an `HSplitView`; the list keeps at least 38% of the tab's width and the tab a least height of 460 points, the sizes it owns ([ui-layout.md](ui-layout.md)).

### Phone Jobs screen

`apps/ios/Sources/YorozuIOS/Jobs.swift`, shown only while the Mac negotiated `jobs-v1` (`PhoneModel.jobsSupported`); wire in [ios-relay-contract.md](ios-relay-contract.md#jobs).

- The Sub-chats list starts with a Jobs row ("N jobs", and "· M need attention" in amber, counting Needs approval and Needs attention). Job topics leave the topic list and the running count.
- `JobsScreen`: one row per job of the latest `job_list`: name with a state badge, the schedule in words, "Next: …" ("Paused", "Not scheduled"), and the last result ("Done", "No change" for a finished run that was not notable, "Failed", "Stopped", "Interrupted", "Running since …", "Not run yet"; for Needs attention "Open to retry or stop", for Needs approval "Its script waits for your yes. Open to answer."). A … menu and trailing swipe actions offer Run Now, Pause or Resume, and Delete after a confirmation ("It stops running. Its sub-chat and its folder stay on your Mac."). Each tap sends one `job_control` while `.paired`, never queued; that job's actions stay off until the Mac's answer, and a refusal shows under the row.
- A tap opens the job's sub-chat (`TopicScreen`, titled with the job's name, the schedule as subtitle; a job without a topic yet does not open) with the job input at the bottom: the composer without files, sending a `message` with `jobId` through the outbox with the usual marks (#314). Every other sub-chat stays inspect only. A `job_result` whose task card already shows the result is hidden like a `result`; a `job_note` is a system row.
- The list lives in memory only: after a launch, Jobs and the job input show once the Mac's handshake reaches the phone.

### Where job messages show

`Message.jobOnlyKinds` (`job_run`, `job_input`, `job_result`, `job_note`) stay in the job's sub-chat (Settings › Jobs on the Mac, the job's sub-chat on the phone): the Mac's main chat (`AppModel.timeline`) and the phone's (`PhoneModel.timeline`) leave them out, the thread list's last activity ignores them, and `Store.search` (phone search) does not match them. To phones: `EngineBridge` never sends a `job_run` trigger (catch-up pages, live updates and page replies skip it and the cursor passes it, so phones see gaps in `seq`); the other three go only to phones that negotiated `jobs-v1`, because `RelayHost` strips them from every `sync_delta` for any other phone, which would show them in its main chat. Approval requests, approval acknowledgments, posted `result`s and failures of job topics are main-timeline messages and show in both. Work in job topics, a deleted job's included (`AppModel.jobTopics`, from the `jobs` bindings), never turns on the Mac's working spinner or the phones' working flag; its task, event and amendment records still reach phones like any topic's.

### Restart

- Queued script steps are never started after a launch: they fail with "Yorozu quit before the script started."
- An uncertain script step (stamped, so the quit cut it short) is not watched or reconciled through a harness and never re-run: it gets one `failure` "“<name>”'s script was interrupted when Yorozu quit; it won't run again by itself. Say retry to run it again or stop to clear it." (`job_interrupted`) and blocks later slots (skip reason `uncertain`) until the user retries or stops it. The Jobs lists show it as "Needs attention".
- AI steps follow [Restart and resume](#restart-and-resume) like other work; their run state is recomputed when they settle. Runs still `running` at launch are recomputed from their steps.
- `AppModel.stop()` removes the wake, clock and zone observers, stops the watcher and the scheduler and terminates running scripts before the Engine shuts down.

## Steer, stop, retry, correct, forget

Replies in quotes are the exact acknowledgments posted to the timeline. Every branch that creates or changes work carries files ([Attachments](#attachments)): a steer's files join the work, and retry, redo and correct carry the original work's.

| Action | What happens |
|---|---|
| `steer` | The work's revision goes up. Queued work that never ran gets the text appended to its instruction (amendment `queued_input`): "Added that to the task before it starts." Otherwise the work becomes `amendment_pending` and a live steer is tried. Admitted: "Sent that change to the running task." Thinking, or an executor that takes changes live (Hermes), not admitted: "I'll apply that right after the current step." An executor that does not: "<executor name> can't take changes mid-run, so it gets this after its current run. Say stop to halt it now." (Claude Code or Codex on OpenClaw). |
| Follow-up turn | When a run ends with pending or unconfirmed amendments, `Store.finish` appends them to the instruction, keeps the old answer as a `superseded_result` event and runs the same task again in the same session. A thinking session gets only the new amendments in that turn ("Follow-up turn of the same task, now revision N…"); it already holds the contract and the earlier turn. An answer that does not echo an accepted (live-steered) revision also triggers one follow-up turn, with that answer kept as `superseded_result`. |
| `stop` | Only for active or uncertain work, else "That isn't running." The work is suppressed first (queued and never run becomes `cancelled`; otherwise `cancellation_requested`), then the Gateway is asked to abort the run. "Stopped." or "Stopping it; not confirmed yet." A step still running locally settles the stop when it ends. |
| `retry` | Only for `failed` or `uncertain` work. With no run ID it counts as stopped. Otherwise the run is reconciled first: running or unknown refuses with "Retry has NOT started…"; completed delivers the result (or runs saved amendments: "The earlier run finished before your change, so I'm applying it now."); stopped retires the old work and delegates new work in the same topic and session with the original instruction, the saved amendments not already merged into it (≤ 10,000 bytes together, head and tail) and "User requested retry: …" (the message ≤ 1500 bytes). |
| Stop and Retry controls | `Engine.stopTask(id:)` and `retryTask(id:)`, for the phone's per-task buttons (owner decision; the buttons come with the 0.7 contract and the phone UI of #313). No secretary call, no `routing` receipt and no user message. They share the typed branches above (`halt`, `retry`): the same guards, reconciliation and acknowledgments, filed in the task's topic and replying to the task's original message (open question 4 default). A retry delegates new work that answers that original message, with its instruction plus the saved amendments. A refusal or error is posted like a typed one, with its own code or `task_control_failed`. Each returns a `TaskOutcome` (`accepted`, `text`, `notice`, `messageID`); an unknown task posts nothing. |
| `correct` | Wrong topic. The mistaken work is stopped or suppressed: "Got it, moving that to the right topic." Then the intended topic's active work of the same executor is steered, an uncertain one gets a saved `pending_reconciliation` amendment, or new work is delegated. History is never moved. |
| New work blocked by uncertain work | See [Uncertain blockers](#uncertain-blockers). |
| `forget` | Needs explicit wording (forget, delete, remove, 忘れ, 削除) and a `memoryID` from the retrieved hits. Queued extraction finishes first, the file is deleted after a SHA-256 check and the index is rebuilt: "Removed that memory from Markdown and refreshed its index. Original chat history is unchanged." |

### Uncertain blockers

Owner decision 7 (`Engine.clearUncertain`). Before a `delegate` inserts new work, each uncertain work item of the same executor in the topic is reconciled. If any blocker is active or suppressed, nothing is reconciled and `Store.insertWork` refuses as before.

- No run ID, or the run is stopped: the old work is retired (suppressed, `failed`) with the acknowledgment "The earlier task here stopped without finishing, so I closed it and started your new request. Its history stays in this topic." The new work starts.
- Completed: the result is delivered and the new work starts. If saved amendments make the old task run again, that runs instead and the new request is refused: "The earlier task here finished before your saved change, so I'm applying that change now. Send this again once it's done, or tell me to add it to that task."
- Running: refused with "An earlier task here is still running, so I haven't started this to avoid running it twice. Say stop to end it, or send this again once it finishes."
- Unknown: refused with "I can't confirm whether an earlier task here is still running, so I haven't started this to avoid running it twice. Say stop to end it, or try again in a few minutes."

Refusals are posted as `failure` messages. A dismiss action for stale uncertain work is not built.

## Restart and resume

On launch, `Store` rewrites unfinished work: rows without a run ID go back to `queued` (or `cancelled` if suppressed); rows with a run ID become `uncertain` with "App restarted while this was running."

`Engine.resume` first routes user messages a quit left unrouted (bug 2 of #313, `Store.unrouted`): `readAt` unset, and, for builds from before `readAt`, no topic, no reply and no work. Those under 24 hours old go through the normal routing queue once, oldest first. An older one is stamped and gets one `failure` reply, "Yorozu was closed for more than 24 hours; send this again if it still applies." (notice `closed_too_long`), and is not routed. A message whose routing had started (`readAt` set) is left alone, even if routing never finished (open questions 2 and 3 defaults). The `sync-r1` migration set `readAt = created` on every existing user message, so history is never routed again. Phone messages the relay held while the Mac was away arrive after launch as replays and go through `EngineBridge.admit` like live ones: past their 24-hour deadline they are refused as `expired`, else stored with their `sentAt` and routed; a known phone's persisted peer-info result lets them through before the phone itself is online ([Relay replays](#flow-2-a-phone-message-to-the-same-timeline)).

`Engine.resume` then queues the first kind of work again and watches each uncertain run every 20 s for up to 360 checks (about 2 hours). A run found completed is delivered; one found stopped or still unresolved at the end gets "That task was interrupted by a restart. Say retry to continue." Job script steps are the exception: never queued again or watched ([Jobs](#restart)).

Reconcile reads the session transcript, not only `agent.wait`: a thinking run is matched by its run ID on the reply, a coding run by its `<run>:user` turn or `[run <id>]` marker, taking the final non-tool assistant turn after it. That is why a coding worker that runs `build_native.sh --restart`, which kills the app mid-run, still has its result delivered by the relaunched app. On Hermes, reconcile reads `GET /v1/runs/{id}` with the server run id kept in the work's controller key ([hermes-integration.md](hermes-integration.md#steer-stop-and-reconcile)).

## Memory

Notes live under the memory root (`~/Yorozu/memory` in live mode) as `<UUID>.md`; automatic extraction writes `knowledge/<UUID>.md`.

- Format: line 1 is JSON metadata (`id`, `title`, `topicID`, `sources`, `evidence`, `knowledgeType`, `attribution`, `epistemicStatus`, `created`, `updated`, `lineage`), then a blank line, then the body. The file name must equal `id` + `.md`.
- `knowledgeType` is one of `user_fact`, `user_preference`, `user_decision`, `user_belief`, `source_claim`, `generated_analysis`, `topic_synthesis`, `tentative_hypothesis`; `attribution` is `user`, `assistant` or `quoted_source`; `epistemicStatus` is `user_stated`, `unverified` or `tentative`. A `user_*` note needs attribution `user`, status `user_stated` and an `evidence` quote found verbatim in a non-quoted user message among its `sources`. Generated analysis stays `assistant`; source claims stay `quoted_source`; hypotheses stay `tentative`.
- Limits: title ≤ 120 characters, body ≤ 8000 bytes, file ≤ 12000 bytes with lineage, ≤ 16 sources that must be existing message IDs, paths of at most 5 components of `[A-Za-z0-9_.-]`, no secret-shaped text.
- Writes: compare-and-swap on the file's SHA-256 (`null` means create only), an advisory `.writer.lock`, a temp file `.projectx-<uuid>.tmp` with fsync, then `renameat`. An overwrite keeps the note's identity, attribution and type and appends the previous body to `lineage`. A write that lands but fails to re-index returns `indexed: false` and must not be replayed.
- History (owner decision 6): when lineage would push a note past 12000 bytes, its oldest versions move to `<memory root>/history/<id>.md`, an append-only Markdown file with one `## Replaced <ISO 8601 time>` section per version (attribution, epistemic status, sources, then the old body). The history file is written atomically before the note is replaced, so a failure in between leaves a duplicate entry, never a lost version. Writes to paths under `history/` are refused (any letter case), and a forget deletes the note's history file too. Builds from before this change read every `.md` file and fail to launch once a history file exists.
- Index: `memory-index.sqlite` with a `discovery` table (id, title, summary = first 200 characters of the body, path) and an FTS5 `search_trigram` table (trigram tokenizer; the older `search` table is left for builds from before batch 2 that share the cache). It is rebuilt from the Markdown at every launch, before and after every write, and after every forget.
- Search terms (`MemoryStore.terms`): a query splits into runs of letters and digits, kana/kanji runs apart from the rest. Other runs of 3 or more characters are lowercased substring terms; shorter ones are ignored. A kana/kanji run of 3 or more characters becomes overlapping 3-character windows, dropping all-hiragana windows unless the whole run is hiragana (mostly grammar). Kana/kanji runs of 1–2 characters (not a lone hiragana) and 2-character stretches between hiragana in longer runs (東京 in 東京で) are short terms.
- Search: up to 64 terms ORed in a trigram `MATCH`, ranked by bm25. Trigrams cannot match 1–2 characters, so when there are fewer than 8 hits up to 16 short terms are matched with `LIKE` over the title and summary, ranked by how many match. A query with no terms gets no hits. At most 8 notes and 10 KB are returned, read back from the Markdown; a note larger than what is left of the 10 KB is passed over and smaller later ones still fit, and an unreadable or unparseable note is skipped and added to `MemoryStore.skipped`. Matching is lexical over the title and summary only, so it misses paraphrases.
- Strictness: the rebuild reads every `.md` file under the root except `history/`. An oversized, unparseable or misnamed file (a `README.md`, malformed metadata, a name that is not `<id>.md`) is skipped and listed in `MemoryStore.skipped`; at launch the app posts one `failure` message naming up to 10 of them. A symlink or a duplicate `id` still makes the rebuild throw: at launch that leaves the app open but not ready (the error shows in the popover's status line and sending is disabled); later it makes every memory write fail. Keep the memory directory to notes only.
- Extraction: runs serially on `conversation` and `result` messages (never acknowledgments, failures or secret-shaped text) as a raw run on the secretary model. The final prompt stays within `rawPromptCap` (20000 bytes): existing relevant memory goes as `{id, title, excerpt}` items (excerpt ≤ 600 bytes) up to 4500 bytes, and the source body is cut by UTF-8 bytes to its head and tail to fit what is left; a prompt that still does not fit fails the job. A message with attached files gets "Attached files (names and paths only; contents not read):" and one `- <name>: <path>` line per file appended to its body, so a note can cite a file as its source and quotes are checked against that same text; file contents are never read, and sub-chat images never reach extraction (#316). At most 4 proposals, each with a quote found verbatim in the source. Replacing an existing note needs correction wording (actually, correction, instead, changed, 訂正, 変更) and a currently retrieved note. A `memoryJobs` row per message (`saved`, `no_knowledge`, `error_no_replay`, `forget_request_not_extracted`) prevents re-extraction; an `error_no_replay` job keeps its failure reason in `memoryJobReasons` (≤ 500 characters; none when it looks like a secret), a separate table so older builds keep writing `memoryJobs`.
- Worker access: only thinking workers, only through `memoryCall`. Thinking workers also have a shell, so these rules hold for them by prompt, not by sandbox.

## Chat search

`Engine.search(query, limit, offset)` (limit default 50, clamped to 1–500; offset clamped to 0–10,000) searches message bodies and sub-chat worker event bodies over the full history, so phone search can cover sub-chats (#313). It returns `hits` newest first, each a `SearchHit` (thread `main`, `topicID` when filed in a topic, and either `messageID` or `eventID` with its `taskID`, a plain-text snippet and `created`), plus the `total` count of matches across both; `Store.search` does the work. The Mac's ⌘F bar and phone `search_request`s call it.

- Indexes: `messageSearch` over `messages.body` and `eventSearch` over `events.body`, external-content FTS5 tables with the `trigram` tokenizer, so Japanese matches (the same choice as memory search). Triggers on insert, delete and body update keep them in sync with every build's writes. Their migrations (`message-search`, `sync-r1`) fill them once; `INSERT INTO messageSearch(messageSearch) VALUES ('rebuild')` (or `eventSearch`) rebuilds one from its table. A final result is a `result` message; a superseded answer is an event.
- Query: split on whitespace into at most 16 terms, all required. When every term has 3 or more characters, each becomes a quoted phrase in a `MATCH`, with snippets from FTS5 `snippet()`. Trigrams cannot match shorter terms, so a query with any 1–2 character term scans bodies with `LIKE` (wildcards escaped), and the snippet is cut around the first term. Cuts are marked "…".

## Change sequence and history window

The `sync-r1` migration (#313) adds what the 0.7 contract's catch-up needs; `EngineBridge` sends it to phones from PR B of #313 ([ios-relay-contract.md](ios-relay-contract.md#change-sequence)).

- `messages.readAt`: when routing of a user message started (`Engine.route`); nil means never started. The migration sets it to `created` on every existing user message. It is never sent to a model: `RoutingInput` and the worker wire are slim views without it.
- `messages.sentAt` (migration `receipts-sent-at`, #314): the phone's send time (its event `ts`) for a message that came from a phone; nil for one typed on the Mac and for older rows. It drives the delay line and `RoutingInput.messageAge` and is never sent to a model; extraction strips it with `readAt`.
- Change sequence: `topics`, `messages`, `work`, `events`, `amendments` and `readCursor` have a `seq` column, and `changeSeq` holds one global counter. Insert and update triggers bump the counter and stamp the row in the same statement, so every write by any build (`assign`, work and amendment state changes, `readAt`) moves the row's `seq`; the update trigger skips its own stamp. The migration stamps existing rows with distinct values. The `sync-topic-touch` migration adds triggers that re-stamp a topic when a message or work row is inserted with it or moved to it, so an old topic re-entering the window is sent again.
- `readCursor`: the last message seen per thread. `Store.markRead(thread:message:)` moves it only forward in timeline order (`created, rowid`); `readCursor(thread:)` reads it.
- History window (open question 1 default, the union): every message created at or after the earlier of 30 days ago and the 500th newest main-timeline message; job-only messages (`Message.jobOnlyKinds`) neither count toward the 500 nor stay past 30 days. Work is in it when created in it (work answering a job-only message only in the last 30 days), the task of a windowed message, or unsuppressed active or uncertain (so it can still be stopped or retried); topics when created in it or used by windowed messages or work; events and amendments of windowed work; read cursors always.
- `Store.changes(after:limit:)`: the window's rows changed after a `seq`, in `seq` order, at most `limit` (1–1000, default 200), as a `ChangePage` with `more` and `latest` (the counter, the next cursor once `more` is false).
- `Store.page(around:before:after:)`: the message plus up to `before` older and `after` newer ones (default 50 each, at most 500), main-timeline only, in timeline order, inside or outside the window (a search hit outside the phone's cache); nil for an unknown id.
- `Store.cursorBounds()`: the latest `seq` and the smallest `seq` of a windowed message; a phone cursor above the first or below the second is stale and gets the window from its start (`reset`).
- Keyed lookups: `Store.message(id:)` (nil when unknown), `topic(id:)` and `work(_:)`, in place of full snapshots. `EngineBridge` uses `message(id:)` for its duplicate check, and only the change-sequence queries above for catch-up and live updates.

## iOS app

`RootView` shows the pairing flow until a host is linked, then the chat. Pairing takes a scanned or pasted link (or a `yorozu://pair` link) and has the user confirm the relay host and the Mac key fingerprint before saving.

- Cache: `MirrorCache` writes the mirror to one JSON file at most once a second and on going to the background ([setup.md](setup.md#where-data-lives)), trimmed by the phone's clock to the newest 500 stored messages plus every one younger than 30 days and the records they reach, and unsuppressed active or uncertain tasks with theirs. It records whether it was filled with `jobs-v1` (the job-only messages); the first `jobs-v1` handshake on a cache without them drops the cursor once, so catch-up refills the window with them. It is keyed to the pairing's own session key, so a file from another pairing is never read, and is wiped on Remove host and on every new pairing; an unreadable file loads as nothing and catch-up refills it.
- Catch-up: every `.paired` sends `sync_request` from the cursor (the `latestSeq` of the last reply page applied whole) and flushes the outbox (below); a reply page with `more` asks for the next, and a request with neither a reply page nor a chunk in 15 s is sent again. A `reset` page clears the mirror except sent bubbles still waiting for their stored copy. A live update moves the cursor only when it continues from it outside catch-up; one that skips ahead starts a catch-up at once. Chunks are reassembled by `ChunkAssembler`; a broken set is dropped and the deadline asks again.
- Connection status: going to the background saves the shown status (`lastConnectionStatus` in `UserDefaults`, the status and its time only) and closes the socket, unless messages are still Sending (below); coming back or launching shows it, if under 10 minutes old, for up to 3 s while the link redials, or until it is connected or failed, then the real one. - Direct path (#315, `RelayClient`, `LegSocket.swift`): one session object with one in-memory `ChannelCounter` over two socket kinds, `URLSessionWebSocketTask` for the relay and `NWConnection` + `NWProtocolWebSocket` for direct. Settings › Connection › "Direct connection (LAN / Tailscale)" is off by default (`directPathEnabledV2` in `UserDefaults`, never v1's `directConnectionEnabled`); until it is on the phone uses the relay only. Turning it on dials the stored candidates at once, which is when iOS asks for Local Network access; off closes any direct socket. Candidates come from a peer exchange that negotiated `direct-v1`, pass only as private literals (`DirectCandidate.isValid`: RFC 1918 or ULA, plus 100.64.0.0/10 for `vpn`), and live in the Keychain pairing record (`PairingStore.Stored.directCandidates`), so Remove host and Repair drop them; a pairing without a `roomId` never dials direct, and a `joined` counts only when sha256 of the Mac's key equals that `roomId`. Race: direct candidates at t = 0, the relay about 300 ms later (at once with no candidates or once every direct leg has failed). Gating (`NWPathMonitor`): `lan` candidates only with Wi-Fi or Ethernet up (never over cellular), `vpn` only with an `.other` interface up. Re-race on foreground (`refreshDirect()`), a real path change and failure. A failed candidate backs off 30 s, doubling to 10 minutes, reset by a path change or by a session of its own that reaches `.paired`; a 4000 close (the Mac is asleep) backs off every candidate so the race takes the relay, and a 4002 close (superseded) backs off none and re-races at once. A healthy direct session is never given up for the relay; a failed one re-races at once. Heartbeat: a direct ping every 10 s with a 5 s deadline (the relay keeps 30 s and 10 s). A socket held back with `.localNetworkDenied` waits out its 10 s deadline, then its candidate is skipped until the next foreground or toggle and Settings shows one line pointing to Settings › Privacy & Security › Local Network. Diagnostics: Path ("Direct · Wi-Fi", "Direct · Tailscale", "Direct · VPN", "Relay", from `TransportUpdate.path`), the direct addresses and the last direct error; the chat never shows the path.

## Markdown rendering

`ChatMarkdown.blocks` in `Sources/ProjectXApp/ChatMarkdown.swift`, shared by the Mac and iOS apps, parses with `AttributedString(markdown:)` (full syntax, partial parses kept) and splits the result into blocks by `presentationIntent`, because SwiftUI `Text` ignores it; parses are cached by text. `MarkdownBlocks` draws them in a lazy stack: paragraphs and headings as `Text`, lists with markers, quotes with a bar, code blocks with a language label, Copy and horizontal scroll, tables as a `Grid` that scrolls sideways, rules, and local images only (`file:` URLs and absolute or `~` paths; remote images stay links and are never fetched, open question 9). Each block is one lazy row, so a very long answer lays out only what is on screen, and nothing is collapsed or cut: there is no "Show more". Selection is per block; Copy on the message copies the whole answer. User text stays verbatim.
