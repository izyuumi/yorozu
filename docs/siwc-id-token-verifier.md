# Bounded SIWC ID-token verifier

`packages/runtime/src/siwc-id-token-verifier.ts` adds actual signature verification with Node `crypto`, independent of the SIWC devkit. `createSiwcIdTokenVerifier(fetchJwks?, now?)` satisfies `SiwcIdTokenVerifier`; its injected fetch takes an abort signal and returns `{status,body}`. Construction performs no I/O. Missing fetch returns unavailable. `SIWC_ID_VERIFIER_READINESS.productionReady` stays false and native integration stays unwired.

OpenAI directs integrations to verify ID signatures against its published JWKS, then validate issuer, client audience, expiration, nonce and subject. This implementation fixes issuer and JWKS to the documented production addresses. Its additional policy requires a matching authorized party for multiple client audiences. The trusted fixed-endpoint HTTPS transport must supply the key response. [Official ID-token validation](https://developers.openai.com/siwc/website), [local-tool identity validation](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

The explicit policy accepts **RS256 with public RSA keys of 2048–8192 bits**, PKCS#1 v1.5 signature padding, a bounded odd exponent, canonical unsigned modulus/exponent, and exact key ID. It rejects unsigned/other algorithms, private/symmetric keys, duplicate key IDs, encryption/signing key operations, external key URLs, embedded certificates, unknown JOSE header members and critical extensions. Both token JSON segments use strict UTF-8, canonical unpadded base64url and a bounded parser rejecting duplicate keys, escaped duplicate aliases, prototype keys, invalid Unicode, excess depth/nodes and nonfinite numbers. Valid JSON whitespace and UTF-8 remain supported. Signature bytes are verified over the exact original encoded segments.

After a verified signature, only checked identity fields are returned: issuer, exact client audience, subject, expiry/issue time, optional nonce/authorized party. Expiry is strict; issue/not-before clock skew allows at most five seconds. Authorization requires the exact supplied nonce. Refresh has no new authorization nonce; the lifecycle checks the preserved client/subject. Raw tokens, arbitrary profile claims, keys and errors never enter results.

Malformed/unsupported tokens, a bad signature against a valid matching supported key, and signed claim mismatches return `invalid`. Failed/aborted key fetch, missing matching key, malformed/ambiguous key evidence or unsupported key-set policy return `unavailable`. This distinction preserves rotated credentials quarantined by `SiwcAccountLifecycle` until verification can resume. Verification-only recovery never repeats token exchange/refresh.

The fetch runs once per verification with a 30-second abort bound and no retry/cache/URL discovery. Production fetch must restrict TLS and the exact official JWKS route, bound bytes/concurrency, disallow redirects and ambient credentials, and preserve failures without secret diagnostics. Root's concrete account HTTPS transport offers `fetchJwks(signal)` for this seam; it remains unwired to a native account service.

Strict all-key RSA policy is a deliberate **preview compatibility gate**: an actual key set containing other algorithms, `x5c`, unsupported metadata or a changed format will remain unavailable. No actual JWKS endpoint was fetched and no current-provider compatibility or account entitlement is asserted. Real protected OS storage, callback/browser ownership, native account UI command validation, product registration eligibility and authorized live acceptance remain separate work. A verifier cannot turn an injected storage attestation into Keychain protection.

Tests generate synthetic RSA keys only in memory. They verify real signatures, payload/header/signature tampering, alternate padding, weak/confused/private key refusal, duplicate JSON/key-ID rejection, nonce/audience/authorized-party/time checks, canonical encodings, generic unavailable errors and cancellation. A lifecycle integration test preserves a real signed rotated token across missing-key evidence/reconstruction, then verifies it without another token request. No file/credential/key read, Keychain operation, network request, browser or callback listener runs.
