# Host SIWC account lifecycle

`packages/runtime/src/siwc-account-lifecycle.ts` implements account lifecycle logic using trusted injected native services. Its constructor opens nothing. `productionReady:false` and `nativeIntegration:"unwired"` remain explicit even when synthetic services work. This change performs no sign-in, network request, callback listen, browser operation, Keychain access, credential-file access or inference. Existing accounts are not imported.

## Protocol and API

OpenAI's public local-tool flow begins new registration with `dynamic_agent_client`; code exchange uses the callback-issued `oaiapp_...` client. Returning authorization reuses the saved issued client and stable host ID, omits the app-name hint, and can supply the retained ID-token hint. Fresh state/nonce/PKCE-S256 protect each attempt. The callback stays HTTP numeric `127.0.0.1`, with fixed `/auth/callback` and only its port variable; exchange uses the exact attempt URI. Identity validation precedes account activation. [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

`new SiwcAccountLifecycle({hostId,appName}, services?)` requires a pre-established protected snapshot with that exact host/app identity. It does not generate or migrate host identity. Omitted/unavailable services produce unsupported status and no authorization plan. Host-only methods:

- `beginSignIn({accountBindingId,callbackPort,returning})` returns an in-memory one-time `attemptId`, exact `callbackUri`, expiry and sensitive `authorizationUrl`. The trusted host must already own the callback listener. Nothing opens the browser. URLs containing ID-token hints must never enter renderer state, logs or transcripts.
- `completeSignIn(attemptId,callbackUrl)` consumes the attempt before asynchronous work; validates exact callback, state, duplicate/unknown query fields and issued client; persists the exchange hold; exchanges once; persists quarantined credentials; verifies identity; atomically adopts and activates.
- `verifyPending(binding)` resumes verification of protected pending credentials after a verifier outage/restart. It cannot repeat token exchange or refresh. Unresolved exchange/refresh holds stay unknown; recovery requires an explicit fresh authorization, never automatic replay. Incomplete first registration without a verified identity needs a separately reviewed native recovery operation; this module offers no destructive cleanup shortcut.
- `getAccessToken(binding,signal?)` is exclusively for the trusted inference broker. It returns the existing `SiwcAccessToken` shape, including exact binding/client/subject and host-verification/storage attestations. It never returns refresh or ID tokens. Those attestations require real native services before use.
- `selectAccount(binding)` selects only an already validated ready registration. `signOut(binding)` immediately fences its execution brokers and cancels pending sign-in attempts. `status()` returns at most 32 opaque bindings, safe phases, active selection, plan-use permission, revision and remote-revocation result. `close()` fences all observed accounts and aborts pending transport/verifier calls.

Same subjects can have separate clients/workspaces. Email is not an identity key. New sign-in leaves another active registration intact until validated durable adoption. Returning sign-in must match the exact saved host/client/subject; callback omission of its client is permitted, substitution is rejected. Identity-only granted scopes retain the validated registration with `planUse:false`; inference is refused. Foreign/unrequested scopes are rejected. [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [permission and recovery rules](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

## Protected state and crash behavior

`SiwcProtectedAccountStore` is an interface, **not implemented Keychain storage**. It must provide OS-protected storage with no plaintext fallback, a crash-safe interprocess lock per account, and durable atomic revision-CAS replacement of the complete snapshot. The snapshot protects registration, credentials and pending credentials together; active selection joins the same commit. Native store initialization, provider identity, key access, corruption handling, backup/upgrade policy and lock exclusion require implementation and physical evidence. A local JS mutex alone is insufficient.

Every exchange/rotation writes a durable hold before token dispatch. Unknown remote response, malformed rotation or a lost durable commit receipt cannot reuse the old rotating token. Successful credentials first enter `pending-verification`; only validated credentials become ready. A transient verifier failure preserves the protected pending state, including the replacement refresh token, for verification-only recovery. An uncertain store commit disables the current lifecycle instance. Durable unresolved phases remain unknown after reconstruction. Global revision conflicts stop that operation; there is no hidden retry of remote effects.

Refresh replaces access token, expiry, scopes and replacement refresh token together, with the saved issued client/resource and no scope parameter. A new ID token requires fresh verification of issuer/client/subject; no new authorization nonce is invented for a refresh. A refresh without a new ID token retains the established verified identity. Access-token lifetime is bounded to the documented one hour. Optional `earliest_refresh_at` currently accepts only nonnegative integer Unix seconds; other formats remain a compatibility gate. [Token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference).

Sign-out keeps registration identity and clears all local tokens after an attempted discovered official revocation. It reports unconfirmed for failed/ambiguous revocation. An old-token HTTP 200 following an unknown rotation cannot establish revocation of an unseen replacement. Repeated sign-out preserves the durable result. The user can disconnect the app in ChatGPT Settings when remote retirement was not confirmed. A synchronous `stopAccount(binding)` callback must fence every exact account execution across host owners; storage failure must not prevent that stop. Native broker-current checks must reject credentials from a retired execution even across separate service instances. [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).

## Remaining native seams and tests

`SiwcAccountTransport.request` accepts GET discovery and form POSTs at fixed official endpoints; it must enforce HTTPS trust, fixed routes, no redirects/ambient credentials, bounded bodies and abort. `SiwcIdTokenVerifier.verify` must cryptographically verify the official JWKS with a strict algorithm/key policy. This module rechecks issuer, client audience/authorized party, subject, expiry, issue time and saved authorization nonce; injected claims do not themselves prove a signature. Native browser/callback ownership and trusted UI command sender validation remain absent. Native service availability, registration/distribution eligibility, actual grant/response formats, protected-store failure/upgrade behavior and real provider round trips remain release gates. No SIWC devkit dependency or implementation code is copied. [Official ID-token validation](https://developers.openai.com/siwc/website), [official SDK storage boundaries](https://github.com/openai/sign-in-with-chatgpt-devkit/blob/main/docs/security.md).

The focused tests use only synthetic credentials/claims and an in-memory revision-CAS store. They exercise exact parameter shapes, fresh values, callback/identity/scope rejection, account separation, durable pre-dispatch holds, multi-instance serialized rotation, pending verification across reconstruction, commit uncertainty, terminal refresh errors, sign-out races, revocation uncertainty, status redaction, cancellation and unsupported services. They establish lifecycle behavior, not native cryptography, TLS, store protection or account entitlement.
