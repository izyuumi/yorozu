# SIWC inference broker and account prerequisites

Checked against public OpenAI documentation on 2026-10-04. This is a host-only relay primitive with inert tests. Native onboarding and production provider transport are **unsupported/unwired**; this change establishes no registration, eligible account, consent, credential storage, paid inference, or release readiness.

## Supported route and eligibility

OpenAI documents app-specific Sign in with ChatGPT OAuth and direct Responses inference for open-source/local tools. Eligible users currently have Plus or Pro and must grant separate plan-use permission. Selected commercial partners have a limited trial; paid or remotely hosted commercial offerings need the partner process. Yorozu's distribution/registration eligibility remains unverified. The reviewed authorized source has no implemented dynamic registration or issued app client; that does not establish whether a registration exists elsewhere. [Quickstart](https://developers.openai.com/siwc/quickstart), [plan-use overview](https://developers.openai.com/siwc/token-sharing-open-source), [client ID process](https://developers.openai.com/siwc/request-client-id), [partner interest form](https://openai.com/form/sign-in-with-chatgpt-interest/).

The minimal future user action is **Continue with ChatGPT**, choose the intended eligible account/workspace, and approve plan usage in the OpenAI browser flow. Identity-only consent does not enable inference. No login, grant, model request, or account probe was performed for this work. [Quickstart](https://developers.openai.com/siwc/quickstart).

Pinned Hermes 0.21.5 (`f97608f178d1ffeca59860195ab7da295f7c8e5f`) implements its own `openai-codex` subscription login. Its source uses the fixed Codex client and `chatgpt.com/backend-api/codex`: `hermes_cli/auth_constants.py:70`, `auth_codex.py:_codex_device_code_login`, `refresh_codex_oauth_pure`, and `agent/codex_headers.py:codex_cloudflare_headers`. This establishes Hermes's project support. The primary OpenAI documents reviewed do not establish authorization for third-party use of that legacy client/backend route. The new broker accepts only fresh app-specific SIWC metadata and fixes the destination to the documented public route; it has no legacy-auth import or fallback.

## Native account work still required

The registration flow needs a stable host identifier, the actual app name, and first-time `client_id=dynamic_agent_client`. Save the callback's issued `oaiapp_...` client per account/workspace and reuse it; never exchange with the entrypoint ID. The public direct flow requires no client secret or partner API key. Start authorization at `https://auth.openai.com/api/accounts/authorize`; use fresh state, OIDC nonce, PKCE-S256 and an HTTP `127.0.0.1` callback. Keep the callback scheme/host/path fixed and the exact selected port URI through the exchange. Request identity/offline scopes plus `resource.invoke` and `chatgpt.tokens.use.direct`, resource `https://api.openai.com/v1`. Exchange at `https://auth.openai.com/api/accounts/oauth/token`. Before adopting the account, verify ID-token signature, issuer, audience, expiry, nonce, subject and granted scopes; reject mismatched returning client/identity. These steps are prerequisites, not implemented behavior. [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

The access token is resource-bound to `https://api.openai.com/v1`, issuer `https://auth.openai.com`, with a documented one-hour lifetime. Refresh tokens rotate, with a 30-day lifetime renewed after successful refresh. A future account service must serialize refresh per session and replace the refreshed record atomically using its issued client/resource, with no scope override. [Token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference).

Proposed Mac implementation: keep token material and stable registration identity in native Keychain-backed storage; restrict access to the account service; retain one validated account/workspace binding per agent; revoke active execution brokers on sign-out/revocation. The official SDK security guide requires app-provided OS-backed encryption with no plaintext fallback. This broker performs no JWT validation, token refresh, persistence, renderer transfer or Keychain operation: its attestation fields are trusted host inputs, not proof of onboarding. [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [official SDK security](https://github.com/openai/sign-in-with-chatgpt-devkit/blob/main/docs/security.md).

No SIWC devkit dependency is added. Its current Noncommercial License requires separate permission for anticipated commercial uses, including covered development/testing. Public protocol documentation is used directly; product distribution eligibility must still be settled. [Official devkit license](https://github.com/openai/sign-in-with-chatgpt-devkit/blob/main/LICENSE).

## Integration API and authority

`packages/runtime/src/siwc-inference-broker.ts` exports:

- `createSiwcExecutionBroker(grant, transport)`: no socket, account lookup, file access or network call at construction. `dispatch` supports inert tests; `handler` adapts Node HTTP without listening. `selected("127.0.0.1", port)` returns the exact `SelectedAgentBroker` primitive accepted by `curated-agent-runtime.ts`.
- `createSiwcBrokerSelector({selectGrant, transport, openEndpoint})`: callable `selectBroker(agent, execution)` for the curated factory, memoized by immutable agent/execution/account/model. `selectGrant` returns nothing until validated onboarding and host-minted execution authority exist. Host callbacks get abort signals and have bounded startup. `release(agentId, executionId)` retires an execution permanently; `close()` aborts active requests and releases owned endpoints. A new execution requires a new bearer.
- `normalizeSiwcRequest`: typed rejection of unsupported payloads rather than implicit provider adaptation. `SIWC_ONBOARDING.status` remains `unsupported`.

The host supplies the exact scope digest, permitted native function names, model, account identity and request/concurrency/byte/deadline budget. Its `isCurrent()` closure must fence stale binding revisions, origin Stop, unknown execution and teardown. Neither the plugin nor a request supplies new authority. The scope digest is a host attestation; OS file/exec/network enforcement and tool permission checks remain the supervisor's responsibility. Restricted handoffs receive a distinct grant and execution/bearer; ordinary per-agent daemons may share their broker across that agent's owned conversation threads.

`openEndpoint` must acquire an independently approved numeric loopback listener, with only its exact port granted to the execution sandbox. The module never acquires a listener itself. The injected transport receives exactly `POST https://api.openai.com/v1/responses`; production wiring must pin HTTPS/TLS, deny redirects, forward no ambient credentials and honor abort/backpressure. No real HTTPS transport is supplied here. Only the fresh local bearer appears in the private runtime provider bootstrap; provider tokens stay inside the host transport callback. Returned status/catalog records and generic errors contain no provider credential.

## Request and stream contract

Direct SIWC uses the public Responses endpoint with `store:false`, `stream:true`, and explicit stateless context. Backend API inference is excluded. [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference).

The relay implements the documented eager function subset by removing flat request `tools` and prepending one `{type:"additional_tools",role:"developer",tools:[...]}` input item at a consistent position. It preserves function names, JSON schemas, `call_id`, arguments and `function_call_output`; SSE passes the same function call identity back. It executes no tool and makes no continuation request. Hermes retains its native provider/tool/orchestration loop. The fixture uses the public `get_customer` example, not a recorded model response. [Documented additional tools schema](https://developers.openai.com/api/docs/guides/tools-tool-search#add-tools-at-a-specific-point-in-the-input).

Unknown fields, client-injected additional-tools items, system messages, unsupported input/attachment forms, names outside the host allowlist, namespaces, custom/deferred tools and hosted tools are rejected. `max_output_tokens`, `prompt_cache_retention`, HTTP `previous_response_id`, metadata, background and multi-agent payloads are forbidden. There is no guessed namespace/call-ID remapping. [SIWC preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

Every forwarded request forces `service_tier:"default"`; legacy `normal` normalizes to this standard tier, while priority/flex/auto are rejected. A reported nonstandard response tier stops the stream. Actual SIWC acceptance of the pinned Hermes payload/tier remains a release gate. [API standard/fast tiers](https://developers.openai.com/api/docs/guides/fast-mode).

Request body, response body, SSE frame, aggregate bytes, concurrency and lifetime are bounded. Downstream writes are awaited before another provider chunk is read. A stream requires provider terminal evidence; EOF, timeout, cancellation, malformed events, unauthorized tool calls and failed responses end with generic uncertainty. No provider error body is forwarded, no retry is attempted, and no API billing or legacy Codex fallback exists. Provider tokens are not written to events or logs. The host must preserve unknown execution rather than replaying an action. [Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

## Evidence and remaining gates

The focused suite uses injected tokens, async byte generators, sinks and endpoint callbacks. It performs no listen/connect, account access, credential read or inference. It verifies binding and consent metadata checks, documented tool conversion, exact call identity, unsupported fields, budgets, secret-error suppression, fragmented UTF-8/CRLF SSE, terminal uncertainty, backpressure, cancellation and irreversible execution retirement.

Before enabling this route: settle applicable registration eligibility; implement native browser callback/ID-token verification/Keychain/refresh/revocation; wire the approved endpoint and constrained HTTPS transport; derive exact function allowlists from the scoped catalog; verify actual pinned Hermes requests against the SIWC preview (notably its optional output-limit/cache fields); validate standard tier, tool result round trips and unknown/Stop behavior with an explicitly authorized fresh account. Installed account adoption and legacy `openai-codex` credential copying are outside this design.

Pass the pinned source via `--source`, owned scratch via `--scratch`, and a scratch file via `--output`. Check the source Git SHA against the pin above first; the script additionally verifies five source-file hashes. No AIAgent, Gateway, native loop, account or real inference is created.

The committed `packages/runtime/src/fixtures/hermes-siwc-shape.json` retains synthetic wire bodies and native function normalization evidence; its test passes normal root, eager function, returned function result and SDK timeout shapes through `normalizeSiwcRequest`. The normal source defaults **omit** `max_output_tokens` and `prompt_cache_retention`: `tui_gateway/server.py:_make_agent` passes no `max_tokens`, `run_agent.py:AIAgent.__init__` defaults to `None`, and the isolated Yorozu profile supplies no request/extra-body overrides. `agent/transports/codex.py:_default_prompt_cache_retention_for_request` adds retention only for specific Meta/Bedrock hosts, so the exact numeric-loopback broker route gets none. This proves the ordinary text + one completed flat function/result **request-shape subset** only. `agent/chat_completion_helpers.py:_build_codex_kwargs` forwards explicit or ephemeral output limits to `ResponsesApiTransport.build_kwargs`; its nonbackend branch emits `max_output_tokens`. Even an initially unset limit may become `_ephemeral_max_output_tokens` during length/truncated-tool continuation (`agent/turn_iteration_prep.py:540`, `agent/turn_truncation.py:335/573`). Those recovery requests stay unsupported at the broker boundary. Supporting them requires an upstream-supported SIWC-aware request/recovery path or an explicit host-visible refusal; it cannot be fixed by quietly discarding a requested token cap. Auxiliary requests, full request middleware, attachment/history variants and live provider acceptance remain unverified release gates.
