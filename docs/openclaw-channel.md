# OpenClaw SDK surface for the Yorozu channel

This page lists what `plugins/openclaw-yorozu` relies on from OpenClaw, and the Gateway behaviour that shaped it. The plugin's own behaviour is in [its README](../plugins/openclaw-yorozu/README.md). Statements about OpenClaw internals come from the OpenClaw source at the minimum version in `package.json` (`peerDependencies.openclaw`, `>=2026.9.8`). Check them against the OpenClaw source before relying on them for a newer version.

## Trust level

A `--link` install is an untrusted plugin. The plugin is designed around that:

- No `api.runtime.gateway.request`. That call is limited to trusted plugins, so the plugin cannot call Gateway RPCs such as `sessions.list`, `chat.history` or `cron.list`. It reads and writes the session store directly (`openclaw/plugin-sdk/session-store-runtime`) and reads the cron store directly (`cron-store-runtime`).
- It cannot claim that a sender is the owner. A Yorozu turn is a non-owner turn unless `commands.ownerAllowFrom` contains `yorozu:owner`; without it, OpenClaw's owner-only agent tools are denied ([setup.md](setup.md#owner-only-tools)).
- Chat, media, typing, tool progress and cron delivery work without trust.

## Behaviour the plugin depends on

- **`startAccount`** must stay pending while the account runs, and stop soon after `abortSignal` aborts. The plugin redials the relay itself instead of throwing.
- **CLI process**: `openclaw yorozu …` runs in its own process and cannot see the channel's memory, so each command calls a Gateway method that the plugin registers (`api.registerGatewayMethod`, scope `operator.admin`). The CLI is declared both in `registerCliMetadata` and in the manifest's `cliCommands`.
- **Session key**: `resolveAgentRoute` with `dmScope: "per-channel-peer"` and peer `owner` gives `agent:<agent>:yorozu:direct:owner`, and `resolveThreadSessionKeys` adds `:thread:<convId>`. OpenClaw lowercases session keys, so `convId`s are lowercase.
- **`/new` and `/reset`** reset only the thread session. The `sessionId` and the transcript stay the same, and a reset event is appended to the transcript. History shows it as a `reset` item. `label` and `displayName` survive the reset.
- **Tool progress**: the plugin passes `replyOptions.onToolStart` and `onItemEvent`, with `allowToolLifecycleWhenProgressHidden` and `suppressDefaultToolProgressMessages`. Without those two flags, tool callbacks depend on verbose mode, and tool summaries would arrive as text.
- **Replies**: whole messages, not streamed (`disableBlockStreaming`). They are chunked by `resolveTextChunkLimit`, which reads `channels.yorozu.textChunkLimit` with 4000 as the fallback.
- **Reply targets**: `buildChannelInboundEventContext`'s `messageId` becomes `MessageSid`, and `supplemental.quote` (`id`, `body`, `senderAllowed`) becomes `ReplyToId` and `ReplyToBody`, shown to the agent as "Reply target of current user message". Outbound, a channel without its own `threading.resolveReplyToMode` defaults to `all`, which puts the current message's id on every reply; the plugin returns `off`, so only `[[reply_to_current]]`, `[[reply_to:<id>]]` and the message tool's `replyTo` reach `deliver`, `sendText`, `sendMedia` and `sendPayload` as `replyToId`. `capabilities.reply` is descriptive only.
- **Reactions**: inbound, `enqueueRoutedSystemEvent(text, { agentId, sessionKey }, { contextKey, replace })` (`openclaw/plugin-sdk/system-event-runtime`) queues a `System:` line for the session's next turn; it never wakes the agent. Outbound, the shared `message` tool's `react` reaches `plugin.actions.handleAction` once `describeMessageTool` lists `react`; `resolveReactionMessageId` falls back to the turn's `MessageSid`, and the conversation comes from `params.threadId`, `toolContext.currentThreadTs` or the session key's thread suffix. `capabilities.reactionSlots: "single"` tells core's session-reaction mirror to replace rather than stack.
- **Cards** (Message Presentation, read-only): the `message` tool's schema gets `presentation` only for a channel whose `describeMessageTool` lists the capability `presentation`, so the plugin lists it, and `agentPrompt.messageToolHints` tells the agent that the conversation is in Yorozu, when a card fits, and to put the key facts in the text too (older apps show only the text; the app shows the text bubble, then the card, and only the card for a card-only reply, whose text is the card's fallback). A card reaches the plugin on two paths, and `sanitizePresentation` (`src/presentation.ts`) checks it on both:
  - **Internal-ui / `deliver`**: on hosts without `channels.yorozu`, a `message` tool send to the current conversation uses the internal-ui sink (`message_tool_only`) and reaches `deliver`, as does a turn's own reply. The payload arrives at `deliver` with `payload.presentation` normalized by `normalizeMessagePresentation` but not adapted to the channel's capabilities, and `renderPresentation` is never called. The plugin's sanitizer is the only gate there.
  - **Outbound / `renderPresentation` → `sendPayload`** (`deliverOutboundPayloads`): on hosts with `channels.yorozu`, `messaging.targetResolver` recognizes `owner` and `threading.resolveAutoThreadId` supplies the turn's convId as `threadId`, so a `message` tool send to that conversation takes this path. Explicit-target sends and cron deliveries use it too. Core adapts the card to `outbound.presentationCapabilities` (tables, charts, context and dividers yes; buttons and selects no) and calls `outbound.renderPresentation` (`renderPresentationForDelivery`, `src/channels/plugins/outbound/presentation-delivery.ts`). Core strips `presentation` from what that returns, so the sanitized card rides in `channelData.yorozu.presentation` (the plugin's `renderedPayload`, `src/cards.ts`). For `null`, core sends its own flattening of the unsanitized card as `text` (`presentation-delivery.ts:69-83`). So the plugin returns `null` only when there was no card; for a card it drops, it logs its dropped-card line and returns the payload with its own text. With `presentationTextMode: "fallback"`, core has already blanked `text` before this call and sends the authored text for `null`, so the plugin returns `null` there and still logs.
    - In OpenClaw 2026.9.8 core calls `outbound.sendPayload` only when the rendered payload has `presentation`, `interactive`, `channelData`, `location`, `audioAsVoice` or `videoAsNote` (`payloadRequiresDurablePayloadTransport`, `src/channels/message/capabilities.ts:52-70`, used at `src/infra/outbound/deliver-core.ts:323-330`). So plain cron text and media still go through `sendText` and `sendMedia`, unchanged, and so does text sent after `null`.
    - An outbound send routed to a thread session (`resolveOutboundSessionRoute`) is mirrored into that transcript as an assistant message with the sent text. The plugin's history finds that message by its text and shows the live reply, with its card, in its place instead of adding a second copy (plugin [Cards](../plugins/openclaw-yorozu/README.md#cards)). Checked on OpenClaw 2026.9.8 with `channels.yorozu` set: a card sent this way came back from history once.
  - **Keyed state for cards**: the plugin opens namespaces `presentations` and `presentation-index` with `maxEntries: 10_000` and `overflowPolicy: "evict-oldest"`, a cap by row count, not bytes (10,000 cards near 64 KiB can take about 640 MB). OpenClaw limits each value to 1 MiB of UTF-8 JSON (`src/plugin-state/plugin-state-store.kernel.ts:21`, `plugin-state-store.validation.ts:107-118`, `plugin-store-validation.ts:221`) and each key to 512 UTF-8 bytes. The plugin's 5 s deadline covers a store call that rejects, never settles, or is still queued behind another write. The store's calls are synchronous (`DatabaseSync`), so one that hangs blocks the event loop and with it the deadline's timer. Rows are plaintext on the host, like transcripts; only the wire is encrypted. OpenClaw's archived transcript keeps the agent's tool-call arguments, card included, outside the plugin store.
  - **What the plugin does with them**: sending, the running turn, keys, history, deadlines, delete and orphan cases are in the plugin's [Cards](../plugins/openclaw-yorozu/README.md#cards). Both paths send cards live; history shows a card only when it was stored, which needs a running turn in its conversation and a store that answers.
- **Titles**: OpenClaw titles only its own dashboard and node sessions, not channel thread sessions. So the plugin calls `generateConversationLabel` itself; it tries the agent's `utilityModel` first, then the primary model. A manual `label` wins over `displayName`.
- **Session-store writes** skip `sessions.patch` validation, including label uniqueness. `preserveActivity: true` leaves `updatedAt` alone. `subscribeSessionChanges` fires for these writes and for changes made through the Gateway.
- **Cron delivery** (`delivery: { mode: "announce", channel: "yorozu", to: "owner", threadId: "<convId>" }`) needs:
  - a configured, enabled account (`listAccountIds`, `inspectAccount`);
  - `outbound.sendText`;
  - `messaging.resolveOutboundSessionRoute`, so the transcript mirror goes to the thread session. Only text is mirrored, and only when the session entry already exists.
- **`openclaw cron add --thread-id`** accepts only positive integers (Telegram topic ids). A job that delivers into a Yorozu conversation is made with the agent's cron tool or `cron.add`.
- **Media**: outbound media paths must be under `getAgentScopedMediaLocalRoots(cfg, agentId)`. `sendMedia` is called once per file, with the caption on the first.
- **Auto-update checks**: OpenClaw exports no helper that says whether its auto-updater can run, so the plugin repeats its checks: the `update.auto` and `update.checkOnStart` config, `OPENCLAW_NO_AUTO_UPDATE`, and the service marker `OPENCLAW_SERVICE_MARKER=openclaw` with `OPENCLAW_SERVICE_KIND=gateway`, which the service environment from `openclaw gateway install` carries on every platform. OpenClaw's own supervisor check also accepts other launchd and systemd hints, so a Gateway under a hand-written service gets the "not running as a service" notice anyway. `update.run` and `update.status` need `operator.admin`, so the plugin does not trigger updates.
- **Keyed state store** rows live in OpenClaw's state database. They are not known to be encrypted at rest.

## Gateway gotchas

- **Probing by hand**: `openclaw gateway call <method> --json --params '<json>'`. Use throwaway session keys and delete them afterwards. For anything bigger, use an isolated profile ([plugin README](../plugins/openclaw-yorozu/README.md#trying-it-without-the-main-gateway)).
- **`chat.history` truncates** long text fields and old messages. That is why the plugin reads transcripts from the store.
- **`--link` installs** load the linked directory on each Gateway start. If that directory is removed, every `openclaw plugins` command reports `Configured plugin load path is unavailable` until the plugin is installed again from a path that exists.
- **Console capture redacts** key- and token-like text. That is why the CLI prints the pairing link with `process.stdout.write`.
