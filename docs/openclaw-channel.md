# OpenClaw SDK surface for the Yorozu channel

This page lists what `plugins/openclaw-yorozu` relies on from OpenClaw, and the Gateway behaviour that shaped it. The plugin's own behaviour is in [its README](../plugins/openclaw-yorozu/README.md). Statements about OpenClaw internals come from the OpenClaw source at the minimum version in `package.json` (`peerDependencies.openclaw`, `>=2026.9.8`). Check them against the OpenClaw source before relying on them for a newer version.

## Trust level

A `--link` install is an untrusted plugin. The plugin is designed around that:

- No `api.runtime.gateway.request`. That call is limited to trusted plugins, so the plugin cannot call Gateway RPCs such as `sessions.list`, `chat.history` or `cron.list`. It reads and writes the session store directly (`openclaw/plugin-sdk/session-store-runtime`) and reads the cron store directly (`cron-store-runtime`).
- It cannot claim that a sender is the owner. A Yorozu turn is a non-owner turn unless `commands.ownerAllowFrom` contains `yorozu:owner`; without it, OpenClaw's owner-only agent tools are denied ([setup.md](setup.md#owner-only-tools)).
- Chat, media, typing, tool progress and cron delivery work without trust.

## Behaviour the plugin depends on

- **`startAccount`** must stay pending while the account runs, and stop soon after `abortSignal` aborts. The plugin redials the relay itself instead of throwing.
- **CLI process**: `openclaw yorozu …` runs in its own process and cannot see the channel's memory, so each command calls a Gateway method that the plugin registers (`api.registerGatewayMethod`, scope `operator.admin`). The CLI is declared both in `registerCliMetadata` and in the manifest's `cliCommands`.
- **Session key**: `resolveAgentRoute` with `dmScope: "per-channel-peer"` and peer `owner` gives `agent:<agent>:yorozu:direct:owner`, and `resolveThreadSessionKeys` adds `:thread:<convId>`. OpenClaw lowercases session keys, so `convId`s are lowercase.
- **`/new` and `/reset`** reset only the thread session. The `sessionId` and the transcript stay the same, and a reset event is appended to the transcript. History shows it as a `reset` item. `label` and `displayName` survive the reset.
- **Tool progress**: the plugin passes `replyOptions.onToolStart` and `onItemEvent`, with `allowToolLifecycleWhenProgressHidden` and `suppressDefaultToolProgressMessages`. Without those two flags, tool callbacks depend on verbose mode, and tool summaries would arrive as text.
- **Replies**: whole messages, not streamed (`disableBlockStreaming`). They are chunked by `resolveTextChunkLimit`, which reads `channels.yorozu.textChunkLimit` with 4000 as the fallback.
- **Reply targets**: `buildChannelInboundEventContext`'s `messageId` becomes `MessageSid`, and `supplemental.quote` (`id`, `body`, `senderAllowed`) becomes `ReplyToId` and `ReplyToBody`, shown to the agent as "Reply target of current user message". Outbound, a channel without its own `threading.resolveReplyToMode` defaults to `all`, which puts the current message's id on every reply; the plugin returns `off`, so only `[[reply_to_current]]`, `[[reply_to:<id>]]` and the message tool's `replyTo` reach `deliver`, `sendText`, `sendMedia` and `sendPayload` as `replyToId`. `capabilities.reply` is descriptive only.
- **Reactions**: inbound, `enqueueRoutedSystemEvent(text, { agentId, sessionKey }, { contextKey, replace })` (`openclaw/plugin-sdk/system-event-runtime`) queues a `System:` line for the session's next turn; it never wakes the agent. Outbound, the shared `message` tool's `react` reaches `plugin.actions.handleAction` once `describeMessageTool` lists `react`; `resolveReactionMessageId` falls back to the turn's `MessageSid`, and the conversation comes from `params.threadId`, `toolContext.currentThreadTs` or the session key's thread suffix. `capabilities.reactionSlots: "single"` tells core's session-reaction mirror to replace rather than stack.
- **Cards** (Message Presentation, read-only): the `message` tool's schema gets `presentation` only for a channel whose `describeMessageTool` lists the capability `presentation`, so the plugin lists it, and `agentPrompt.messageToolHints` tells the agent that the conversation is in Yorozu, when a card fits, and to put the key facts in the text too (older apps show only the text). A card reaches the plugin on two paths, and `sanitizePresentation` (`src/presentation.ts`) checks it on both:
  - **Internal-ui / `deliver`**: on hosts without `channels.yorozu`, a `message` tool send to the current conversation uses the internal-ui sink (`message_tool_only`) and reaches `deliver`, as does a turn's own reply. The payload arrives at `deliver` with `payload.presentation` normalized by `normalizeMessagePresentation` but not adapted to the channel's capabilities, and `renderPresentation` is never called. The plugin's sanitizer is the only gate there. A JSON string over 64 KiB is dropped; an object over the limits is trimmed and sent with an omission note. The text is always sent; empty text becomes the fallback text of a card that is sent; a card that cannot be shown is dropped with the exact content-free log line "yorozu: dropped a card that cannot be shown; the reply goes out without it", and the payload then sends exactly what it would without a card (nothing, when its text is empty). The replies go out first; the card is stored after them without being awaited, so a slow or failing store costs the history card (one log line) and never the reply.
  - **Outbound / `renderPresentation` → `sendPayload`** (`deliverOutboundPayloads`): on hosts with `channels.yorozu`, `messaging.targetResolver` recognizes `owner` and `threading.resolveAutoThreadId` supplies the turn's convId as `threadId`, so a `message` tool send to that conversation takes this path. Explicit-target sends and cron deliveries use it too. Core adapts the card to `outbound.presentationCapabilities` (tables, charts, context and dividers yes; buttons and selects no) and calls `outbound.renderPresentation` (`renderPresentationForDelivery`, `src/channels/plugins/outbound/presentation-delivery.ts`). Core strips `presentation` from what that returns, so the sanitized card rides in `channelData.yorozu.presentation` (`renderedPayload` in `src/cards.ts`). Returning `null` (nothing to show) makes core put its own text fallback in the payload's `text`.
    - In OpenClaw 2026.9.8 core calls `outbound.sendPayload` only when the rendered payload has `presentation`, `interactive`, `channelData`, `location`, `audioAsVoice` or `videoAsNote` (`payloadRequiresDurablePayloadTransport`, `src/channels/message/capabilities.ts:52-70`, used at `src/infra/outbound/deliver-core.ts:323-330`). So plain cron text and media still go through `sendText` and `sendMedia`, unchanged, and so does the text fallback after `null`.
    - `sendPayload` (`sendConversationPayload`) sanitizes `channelData.yorozu.presentation` again (a caller can set `channelData` itself), chunks the text by `textChunkLimit` and sends every chunk, with files and the card on the last one. A card that cannot be shown is dropped with the same log line and the text and files go out alone. A payload that reaches it without a card (other `channelData`, a location, or a dropped card) follows the existing text/media path: one reply per text chunk or one `sendMedia` per file, text on the first file only. With no text or files it sends nothing, returns no id and does not throw.
    - `handleMessage` records the running turn by convId (inbound user messageId, routed agent id and session key) from dispatch start until `finally`. A new turn replaces the entry; an older turn ending removes it only if it still owns the entry. When `sendConversationPayload` sends a card into a conversation with a running turn, it resolves the live session id from that route and stores the card under `turnCardKey(sessionId, userMessageId, replyId)`, with the LAST card-bearing reply event's messageId, ts and text. Storage is not awaited and uses the same content-free failure warning as `deliver`. Thus both host paths show cards live and in history, including synthesized text when the transcript assistant message holds only a tool call.
  - **Stored cards**: keyed state namespace `presentations` (at most 10,000 rows, oldest dropped), plus `presentation-index` (key `convId`, the conversation's card keys, at most 10,000 rows, oldest dropped). A reply matched by `liveReplyIds` is keyed by `<sessionId>:<transcript event id>`; only a payload with its own text or files looks up those ids. History puts that card on the matched event's last chunk. Every other card in a turn, including a card-only message-tool payload whose transcript holds only a tool call, is keyed by `<sessionId>:turn:<inbound user messageId>:<live reply messageId>`, with its live reply's messageId, ts and text stored alongside it. History appends it as a separate agent item after that turn's other items, using those stored fields for live/history deduplication; it never attaches it to another reply's text. All stored card content and synthesized items count toward the history page's 192 KiB budget.
    - **Bounds**: an index row holds at most 500 keys; a conversation's 501st card deletes its oldest key and card. OpenClaw limits each value to 1 MiB of UTF-8 JSON (`src/plugin-state/plugin-state-store.kernel.ts:21`, `plugin-state-store.validation.ts:107-118`, `plugin-store-validation.ts:221`) and each key to 512 UTF-8 bytes. A card or prospective index row over those limits is skipped before writing, with one content-free warning (`CardTooLarge`). The namespaces are capped by count, not total bytes; 10,000 cards near 64 KiB can occupy about 640 MB, plus stored reply text and indexes.
    - **Deadlines**: lookups have a 5 s deadline. Writes are queued and have 5 s once they start; an operation that misses its deadline is abandoned and checks that state before each further write. It cannot resume with a stale index write over a later put or recreate a deleted index. A write already handed to the underlying store cannot be cancelled. History lookups use the same deadline; a failing or timed-out lookup yields a page without cards and one content-free warning. A store failure warning carries only the error name/code, never its message or card content.
    - **Delete**: cards are read only through the conversation's index. Deletion is two awaited steps: forget its listed cards and index row, then delete its session entry (also forget cards when the entry is already gone). A failing or timed-out forget returns `error internal` and does not delete the session entry; retrying can finish the deletion. Archiving alone does not forget cards.
    - **Not stored**: an outbound send whose destination conversation has no running turn (including sends after a turn ends or to another conversation without its own turn), a turn with no session id, or a store failure, timeout or size rejection. The card still goes out live; a content-free warning explains that history will not show it. A missing assistant text event alone no longer prevents storage.
    - **Orphans**: a write already handed to the store may land after deletion; an evicted index row can leave its cards unreachable; an abandoned operation may leave a card write already in flight after its index is removed, or an index entry without a card when it times out between the two writes. No further writes run after abandonment. Unreachable card rows cannot be read or deleted through a conversation and age out at the 10,000-row cap; an index entry without a card is ignored by history and removed on delete. OpenClaw's archived transcript still holds the agent's tool-call arguments, card included, outside the plugin store.
    - Like transcripts, rows are plaintext on the host; only the wire is encrypted.
- **Titles**: OpenClaw titles only its own dashboard and node sessions, not channel thread sessions. So the plugin calls `generateConversationLabel` itself; it tries the agent's `utilityModel` first, then the primary model. A manual `label` wins over `displayName`.
- **Session-store writes** skip `sessions.patch` validation, including label uniqueness. `preserveActivity: true` leaves `updatedAt` alone. `subscribeSessionChanges` fires for these writes and for changes made through the Gateway.
- **Cron delivery** (`delivery: { mode: "announce", channel: "yorozu", to: "owner", threadId: "<convId>" }`) needs:
  - a configured, enabled account (`listAccountIds`, `inspectAccount`);
  - `outbound.sendText`;
  - `messaging.resolveOutboundSessionRoute`, so the transcript mirror goes to the thread session. Only text is mirrored, and only when the session entry already exists.
- **`openclaw cron add --thread-id`** accepts only positive integers (Telegram topic ids). A job that delivers into a Yorozu conversation is made with the agent's cron tool or `cron.add`.
- **Media**: outbound media paths must be under `getAgentScopedMediaLocalRoots(cfg, agentId)`. `sendMedia` is called once per file, with the caption on the first.
- **Auto-update checks**: OpenClaw exports no helper that says whether its auto-updater can run, so the plugin repeats its checks: the `update.auto` and `update.checkOnStart` config, `OPENCLAW_NO_AUTO_UPDATE`, and the service marker `OPENCLAW_SERVICE_MARKER=openclaw` with `OPENCLAW_SERVICE_KIND=gateway`, which the service environment from `openclaw gateway install` carries on every platform. OpenClaw's own supervisor check also accepts other launchd and systemd hints, so a Gateway under a hand-written service gets the "not running as a service" notice anyway. `update.run` and `update.status` need `operator.admin`, so the plugin does not trigger updates.
- **Keyed state store** rows live in OpenClaw's state database. They are not known to be encrypted at rest.

## Gateway gotchas

- **Probing by hand**: `openclaw gateway call <method> --json --params '<json>'`. Use throwaway session keys and delete them afterwards. For anything bigger, use an isolated profile ([plugin README](../plugins/openclaw-yorozu/README.md#trying-it-without-the-main-gateway)).
- **`chat.history` truncates** long text fields and old messages. That is why the plugin reads transcripts from the store.
- **`--link` installs** load the linked directory on each Gateway start. If that directory is removed, every `openclaw plugins` command reports `Configured plugin load path is unavailable` until the plugin is installed again from a path that exists.
- **Console capture redacts** key- and token-like text. That is why the CLI prints the pairing link with `process.stdout.write`.
